# Design requirements: client-files

Group: client-files. Audience: client. Route: /files.
Written 2026-09-13 against live code, STATUS.md, TASKS.md, the page catalogue and the design review checklist. Source files read: `app/(dashboard)/files/page.tsx`, `app/(dashboard)/files/files-content.tsx`, `app/api/portal/files/route.ts`, `app/api/uploads/presign/route.ts`, `app/api/uploads/confirm/route.ts`, `app/api/uploads/serve/route.ts`, `lib/upload-access.ts`, `lib/require-feature.ts`, `lib/feature-tree.ts`, `components/tahi/nav-model.tsx`, `db/schema.ts` (files table), and the Claude Design project files `portal-files.jsx`, `portal-files-kit.jsx`, `portal-files-data.jsx`, `portal-files.css`.

## 1. Purpose and audiences

/files is the client portal's file library: everything the studio has delivered to a client, plus anything the client has uploaded for the studio. It is a client-only route. Studio team members never land here in their own session; the only way an admin sees it is by opening Client View / Act mode on a specific client org, at which point the page renders that org's library.

Who opens it: any signed-in contact at a client organisation, in any portal seat (`member` or `admin`). Unlike Invoices, Files carries no `requiresOrgAdmin` gate in the nav model (`components/tahi/nav-model.tsx`), so a plain member seat sees the same page as the org's admin seat.

What it must never show:
- Files attached to an internal request or an internal message. `GET /api/portal/files` explicitly excludes any row whose parent request or message is `isInternal`, so a studio-only attachment never reaches a client (`app/api/portal/files/route.ts`).
- Another organisation's files. `orgId` scoping runs on every read and write; `resolveOwnerOrgForUpload` and `decideUploadRead` (`lib/upload-access.ts`) are the two choke points and both resolve to the caller's own D1 org, never a client-supplied one.
- The Tahi-internal org's files. The portal route 403s outright if the resolved org equals the Tahi org id.
- Anything that reads as a super-admin or studio-only affordance: no "New service", no coupons, no visibility toggles, no client picker. (The exact bug this rule guards against already happened on `/services`, fixed in CL.2, and the same impersonation-cookie pattern is what makes Files safe under Client View today.)
- The Messages-hidden rule does not apply to this page directly (Files and Messages are separate routes, separate feature keys), but the design file bundles both: `portal-files.jsx` exports `window.TahiPortalFiles = { Files, Messages }` and the two share `portal-files-kit.jsx`, `portal-files-data.jsx` and `portal-files.css`. Whoever ports this file must NOT wire up its Messages half onto the live `/files` route, and must remember Messages is hidden from the client nav by default (Liam, 2026-09-13; per-org or per-contact override brings it back). That is a different design requirements group's problem, but it lives in the same source file, so note it here so it is not silently ported alongside Files.
- No fake numbers or dead buttons: every count, badge and the storage meter must either be backed by a real query or be explicitly marked "not built" per section 4. The design's storage quota (`STORAGE.usedBytes` / `quotaBytes`) is a PROPOSAL per its own data file comment: the product has no quota concept today.

## 2. Pages, sub pages and entry points

Only one route in this group, but it has real internal structure.

- `/files` — the page itself. Reached from the client nav ("Library" group, `clientOnly: true`) on desktop, and from the mobile bottom tab bar (`components/tahi/mobile-bottom-nav.tsx` maps `/files` to the `files` icon). No query-string states exist today (no `?folder=`, no `?file=`); the live page has no folders and no per-file detail view to deep-link to.
- Upload entry point: a hidden `<input type="file" multiple>` triggered by the header "Upload files" button (and, in the design, by the empty-state action and a drag-and-drop drop zone over the whole content pane).
- File preview / detail: today there is none — a file row is just a download link. The design proposes a slide-over ("FileDrawer") opened by clicking a card/row, with three tabs (Comments, Versions, Details) and a footer (Download, Share to a request, more actions). This is new surface, not a port of something live; treat it as CL.1's centrepiece.
- Folder navigation: does not exist live. The design proposes a left rail folder tree (desktop) collapsing to a horizontal folder-chip strip (mobile), a breadcrumb bar, and folder cards when a folder has children. Folder ids in the design sample (`brand`, `content`, `contracts`, `deliverables`, per-request auto-folders under `deliverables`, `shared`) do not match TASKS.md's phrasing of the same idea (Deliverables, Brand, References, Uploads) — reconcile the four (or five) standing folder names with Liam before finalising; treat the exact name list as open (section 7).
- Studio lens on the same drive: the design's `Files` component also renders for `audience !== 'client'` (a "Switch client" kebab, "Shared by {client}" labelling). That studio-facing lens is out of scope for this client-only requirements doc — it belongs to a Clients/client-detail requirements group, since the live product currently browses a client's files from the client detail page's Files tab, not a dedicated studio /files route. Note it here so the porting agent does not silently ship a studio nav entry as a side effect of porting the client page.

## 3. States and variants

One line per state, page = /files unless noted.

- **Loading (initial fetch).** Live: `DataTable` renders its built-in loading skeleton via the `loading` prop while `useResource` has no data yet. Design: a 650 ms boot delay then a skeleton grid or skeleton rows matching the current view toggle.
- **Empty (no files at all).** Live copy: title "No files yet", body "Delivered work shows up here. You can also upload brand assets and references for the team.", action = the same Upload button. Design copy: title "Nothing here yet", body "Work we deliver lands here automatically, in a folder per request. Anything you send us sits in Shared by you." Pick one; they currently disagree (see section 7).
- **Empty folder (design only, no folders live yet).** "This folder is empty", with Contracts getting its own read-only copy ("Signed agreements appear here as soon as they are countersigned").
- **Filtered to nothing (design only, no filters live yet).** "No files match" / "No files match", action "Clear filters".
- **Error (fetch failed, no prior data).** Live: `EmptyState` with "We could not load your files", "Something went wrong reaching your library. Try again in a moment.", a Try again button that re-runs `mutate()`. This only takes over the whole surface when there is no cached list; see next state.
- **Stale (fetch failed, prior data still shown).** Live: a warning `Callout` above the table, "This list may be out of date" / "We could not reach your library just now. Anything you uploaded is safe, it may take a moment to appear.", with a Refresh action. The table underneath keeps showing the last good list. This SWR-stale-not-blank behaviour is a real, already-shipped pattern worth preserving in the port.
- **Uploading.** Live: the Upload button switches to a loading/disabled state for the whole batch; there is no per-file progress, percentage or cancel. Design: a bottom-right tray, one row per file, a percent meter, per-row cancel, a running "N of M added" count, and a hard-fail row (over a size cap) that offers Remove only, no Retry, versus a soft/offline failure that offers Retry.
- **Upload partially failed.** Live: each file is tried independently; failures toast individually ("Could not upload {name}. Please try again.") while successes still land and the list revalidates. No cap on file size is enforced anywhere in the upload routes today (checked `app/api/uploads/presign/route.ts` and `confirm/route.ts`) so a very large file can 500 partway through in production; the design's "over 500 MB" hard-fail state is a PROPOSAL cap that does not exist in the backend yet.
- **Read-only client view (studio previewing as this client, or act mode).** Live: the page still renders normally and upload still works, deliberately, with the upload resolver reading the impersonation cookie so bytes land under the previewed org's prefix rather than Tahi's (see `files-content.tsx` comment on `impersonatedOrgId`). This is a real, intentional exception: Files is one of the two client-only routes the middleware lets a preview into. Design disagrees here: it treats "View as client" (`ctx.inPreview`) as read-only, disabling Upload/New folder and refusing drag-and-drop with a toast. Resolve which behaviour is correct for the ported page (see section 7) — do not silently break the working preview-upload path.
- **Member seat versus admin seat.** No difference today or in the design: Files carries no `requiresOrgAdmin` gate, unlike Invoices.
- **375px.** Live: `DataTable`'s `mobileCard` prop renders `FileMobileCard`, a single tappable row (min-height 2.75rem) with name, "{type} · {uploader} · {ago}" and a trailing download glyph; the whole card is the tap target, not a small icon, per the "no hover-only affordance" rule. Design: folder rail becomes a horizontal chip strip, grid view is forced to list, and the file drawer becomes a bottom sheet.
- **768px.** Not specifically tested in either the live code or the design notes; the design's rail-to-strip breakpoint and the DataTable's own responsive breakpoint should both be checked at 768 explicitly, since a folder tree at 768 may not yet need to collapse.
- **Dark mode.** Live: every colour in `files-content.tsx` is a `var(--color-*)` token, so dark mode should fall out for free; not yet live-verified per STATUS.md's portal-wide dark-mode caveat. Design: `portal-files.css` states it uses "shell theme tokens only" (`--bg`, `--bg-secondary`, `--text`, `--text-muted`, `--text-faint`, `--border`, `--border-subtle`, `--brand`, `--brand-strong`, `--brand-100`, `--shadow`, `--ease`, `--radius-leaf`) so dark mode "falls out" there too, but these are the design shell's own token names, not this app's `--color-*` names, so a straight copy-paste of the CSS will not pick up the live app's theme; the port needs a token-name translation pass, the same one every other ported page has needed.
- **Print or public.** Not applicable. Files has no public share link and no print view in the product or in the design.
- **Offline (design only).** A `Callout` reading "This list may be out of date" for Files, or "You are not connected" for the bundled Messages half; uploads/comments/sends fail with a working Retry. Not implemented live (there is no offline detection on this page today).

## 4. Features and actions

### What works today (from the code)
- List the org's external-visible files (`GET /api/portal/files?limit=100`), newest first, with a relative "ago" string, a type chip derived from the file extension, and the uploader's display name resolved from `teamMembers` or `contacts`.
- Upload one or more files: presign (`POST /api/uploads/presign`) → PUT the bytes to the R2 proxy → confirm (`POST /api/uploads/confirm`), each file handled independently so one failure does not block the rest.
- Download any listed file via `/api/uploads/serve?key=...` (per-row link and a trailing "Get" button on desktop; the whole mobile card on phones).
- Correct tenancy: uploads always land under the caller's own resolved D1 org (or the previewed org's, under Client View); serve/confirm both re-check the files row's `orgId` before returning bytes, closing the pre-B1 cross-tenant write hole.
- Loading skeleton, honest error empty-state with retry, and a stale-but-cached banner that never blanks a good list on a failed background refresh.

### What exists but is wrong or half built (from STATUS, TASKS, the catalogue)
- The page catalogue's "current state" column still calls `/files` a "Stub (EmptyState, no fetch)". That is stale: T2.2 (shipped 2026-09-05, per TASKS.md) wired the real fetch and upload flow described above. Whoever runs the design pass should not re-derive requirements from the catalogue's stale description; use this document's section 4 instead, and flag the catalogue line for a correction.
- No search, no type filter, no source (team vs. client) filter, no sort control, no grid/list toggle. The design has all of these; the live page has none.
- No folders. Every file sits in one flat list; there is no per-request auto-folder, no Brand/Content/Contracts/Deliverables/Shared grouping, matching `db/schema.ts`'s `files` table having no `folderId` column at all.
- No storage quota or usage meter (there is no quota concept in the product).
- No per-file detail, no versions, no comment thread, no "share this file to a request" action. A file row is only a name + type + uploader + date + download.
- Rename, move, delete: none exist for a client. The design's per-file kebab menu offers all three, with delete gated so a client can only delete files they uploaded themselves ("Studio file" note on a disabled delete for anything the studio shared).
- Drag-and-drop upload: does not exist live (`files-content.tsx` has no `onDrop`/`onDragOver` handlers); only the hidden `<input>` + button flow.

### What is planned or missing (TASKS, catalogue, Liam's decisions)
- **CL.1** — "Files as a small Google Drive with threads." Folders per client (Deliverables, Brand, References, Uploads per TASKS.md's own wording), drag-and-drop uploads from the client, a comment thread per file (TASKS.md explicitly says to reuse the request-thread composer and the `messages` table with a file target rather than inventing a new comments table), versions optional. Direct quote from Liam recorded in TASKS.md: "i'd like to give them a small version of like google drive but with threads so they can upload docs for us there." TASKS.md is explicit that design happens first, alongside the Clients pages, and that the current `/files` page (list, upload, download) stays live until the redesign ships — so this is an additive rebuild, not a rip-and-replace done blind.
- The catalogue rates `/files` priority 1 (client-facing daily) at roughly 5 agent-days once designed, covering "port and functionality: everything."
- **J1** (catalogue functionality section) restates CL.1 under "Files, notifications and integrations depth": design first.
- A file-size cap is a PROPOSAL only (the design's 500 MB example); there is no agreed number recorded anywhere in TASKS.md or STATUS.md. Needs a decision before it becomes a real upload-route change, not just a design affordance.
- Versions and per-file comment threads are both "optional" per Liam's own CL.1 wording — do not treat the design's fully fleshed-out version history and thread UI as mandatory scope; flag which pieces are must-ship versus nice-to-have when the design pass starts.

## 5. Data and integrations

- **Tables.** `files` (id, requestId, messageId, orgId, uploadedById, uploadedByType, filename, storageKey, mimeType, sizeBytes, timestamps). No `folderId` column exists; CL.1 needs a schema migration before folders can be real (per CLAUDE.md's rule: do not build UI for a feature until its schema is in place). A per-file comment thread is meant to reuse the existing `messages` table with a file target rather than a new table (TASKS.md's explicit instruction) — that also needs schema/route work (a `messages.fileId` or equivalent) before the design's Comments tab can be wired to anything real, not a fake local `comments` array like the design's sample data holds today.
- **API routes.** `GET /api/portal/files` (list, org- and internal-scoped), `POST /api/uploads/presign`, `PUT /api/uploads/proxy` (the actual byte-carrying step between presign and confirm; buffers the request body and writes it to R2 since R2 Workers bindings do not support presigned PUT URLs, and separately validates that the storage key's org prefix matches the caller's own resolved org before accepting the write), `POST /api/uploads/confirm`, `GET /api/uploads/serve` (download/inline), `GET /api/uploads/[fileId]` (not read in depth here, but exists for the admin/detail-level surface). All gate through `getRequestAuth`/`getPortalAuth` plus the org-resolution helpers in `lib/upload-access.ts`.
- **Feature flag.** `files` is a `FEATURE_TREE` key (`lib/feature-tree.ts`), `appliesTo: ['client']`, mapped to route `/files`. `requirePortalFeature` enforces it server-side on the portal list route; a client org can be denied the feature entirely (403 `feature_disabled`), same mechanism the tenancy-isolation e2e suite exercises.
- **Storage.** Cloudflare R2 via the `STORAGE` binding, accessed through `getCloudflareContext()`; no Node `fs`. Storage keys are `{ownerOrgId}/{requestId|'general'}/{timestamp}-{filename}`.
- **Third parties.** None directly (no Stripe, no Xero, no Slack on this surface). The design's "Share to a request" action would touch the `requests` table if built for real.
- **Honesty requirements.** The storage quota meter, versions, and comment "seen" cursors in the design are all PROPOSAL/sample data with no backing column; none of them may ship as visible UI without a real data source behind them, per CLAUDE.md's "no fake numbers" rule repeated in this brief's own instructions.

## 6. Design system contract

- **Primitives already in use live:** `PageHeader`, `Card`, `DataTable` (with `mobileCard` for the sub-768 render), `EmptyState`, `Callout`, `TahiButton`, `Badge`, the shared toast (`useToast`) and the shared impersonation context (`useImpersonation`). Any port must keep using these rather than the design file's parallel primitive set (`Icon`, `Avatar`, `Stack`, `Thumb`, `Pill`, `Meter`, `Segmented`, `SearchBox`, `Kebab`, `Drawer`, `SkelGrid`, `SkelRows`, `Bubble`, `Composer` from `window.PF` in `portal-files-kit.jsx`) — those exist to make the Claude Design prototype self-contained, not as a second component library to import into the app.
- **Leaf radius.** The design already applies `var(--radius-leaf, 0 .625rem 0 .625rem)` to its primary button and nothing else, matching CLAUDE.md's rule to reserve it for icon backgrounds, avatar wrappers, primary CTAs and feature callouts, not every card. Correct usage; keep it.
- **Left rail / headline band.** This is the design's real known defect. DL.2 (the 2026-09-12 consistency pass that unified one headline-band anatomy and one left-rail idiom across `head-band.css`, `requests-kit.jsx`, `ops-kit.jsx`, `ops.jsx`, `sales-pipeline-kit.jsx`, `tasks.jsx`, `clients.jsx`, `portal-home.jsx` and `portal-money.jsx`) did NOT touch `portal-files.jsx`. DL.0's local critic pass flagged "shared band, shared rail, deals and portal-files carry FIX notes to re-check live after the write" (TASKS.md), and the page catalogue records the same verdict: `portal-files.jsx` FIX, "no headline band, third rail idiom [...], flagged low priority." Before this page is ported, its header and its 15rem folder rail need to be brought into the same headline-band and rail pattern the other list pages now share, not left as a fourth idiom.
- **SlideOver.** The live app already has a `SlideOver` primitive (`components/tahi/slide-over.tsx`) used for request/task detail. The design's `FileDrawer` (Comments/Versions/Details tabs, footer actions) should be built on `SlideOver`, not the design's own bespoke `Drawer` component, so it matches the request-detail and task-detail slide-over pattern the rest of the app already uses.
- **What the existing design gets right, worth keeping as-is:** the SWR-safe stale-vs-blank distinction already matches the live page's own pattern; the empty-state, error-state and offline-state vocabulary (leaf-radius glyph, title, description, one action) matches CLAUDE.md's canonical empty/loading/error contract; the mobile folder-chip strip and forced list view are a reasonable 375px answer; the read-only "View as client" disabling of writes is the correct *general* pattern for previews, it is just wrong specifically for uploads on this one page (see section 7); tokens are shell-theme-only so dark mode should carry over cleanly once translated.
- **What must change before port:** the rail/headline-band FIX above; the token-name translation from the design shell's `--bg`/`--text`/`--border` family to this app's `--color-bg`/`--color-text`/`--color-border` family; reconciling the read-only-upload-under-preview behaviour with the live, already-shipped, deliberately-not-read-only upload path; and stripping the bundled Messages component out of whatever gets ported for `/files` (it is a different page's design requirements).

## 8. Acceptance for the design review

1. At 1440 light and dark, the page header matches the same headline-band anatomy now shared by Requests, Tasks, Clients, Ops, Sales pipeline, Portal home and Portal money — not a fourth bespoke header.
2. At 1440, the folder rail (if built) uses the same rail idiom as the other DL.2-consistent list pages, and is either collapsible or narrower than the 15rem the design currently ships when the content pane needs the room.
3. At 375, there is no horizontal scroll and every tappable row/card/button (file row, folder chip, upload button, kebab menu, drawer close) measures at least 44px tall.
4. At 375, the folder rail is replaced by a horizontal chip strip (or is absent if folders are not yet in scope), and the view is forced to a single-column list, never a grid.
5. Every state in section 3 (loading, empty, error, stale, uploading, upload-failed) is present and uses the shared `EmptyState`/`Callout`/skeleton primitives, not one-off markup.
6. Dark mode shows no contrast regression on the folder tree, file cards/rows, the upload tray, and the file drawer (if built), using this app's `--color-*` tokens, not the design shell's raw `--bg`/`--text` names.
7. No visible number is fabricated: a storage meter, a version count, or a comment count only appears if it is backed by a real column/query; anything not yet backed by data is either absent or clearly marked as not-yet-real in the handoff notes.
8. The read-only/Client-View behaviour for uploads matches whichever answer to open question 1 was chosen, and does not silently regress the other.
9. No em or en dash appears anywhere in the rendered copy.
10. The ported page never renders the Messages half of `portal-files.jsx`, and Files never appears for a super-admin-only area or exposes another org's data (spot-check by switching Client View between two seeded orgs and confirming the file list changes).
