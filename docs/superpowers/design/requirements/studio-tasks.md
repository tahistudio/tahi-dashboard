# Design requirements: studio-tasks

Routes: `/tasks` (List, Board, My week), `/tasks/[id]` (redirect shim). Components: `components/tahi/tasks/*`, `components/tahi/ai-task-wizard.tsx`, `lib/task-wizard-drafts.ts`, `lib/tasks-views.ts`, `lib/tasks-planner.ts`, `lib/tasks-quick-add.ts`, `lib/tasks-board-items.ts`, `lib/task-consistency.ts`. API: `app/api/admin/tasks/**`, `app/api/admin/ai/task-wizard`, `app/api/admin/task-templates/**`.

Design file in the Claude Design project: `tasks.jsx` (94,016 bytes) plus `tasks-data.jsx` and `tasks.css`. Catalogue verdict: SHIP (Pass 3, "matches Requests exactly"). Checklist row: ported 2026-09-05, live, not yet reviewed by a human tick. This is the one page in the whole catalogue where the design file and the live code already agree; the only outstanding design-then-build item is TP.3 (My week real dates).

## 1. Purpose and audiences

Tasks is the studio's own to-do list: emails, chasers, prep, housekeeping, and client work that has not (or will never) become a request. It is where Tahi runs itself, distinct from Requests, which is the client-facing work item. The subtitle on the page states this directly: "The studio's own to-do list: emails, chasers, prep, housekeeping. Sometimes for a client, sometimes not."

Who opens it: only Tahi team members (`orgId === NEXT_PUBLIC_TAHI_ORG_ID`). There is no client audience for this surface at all, not even a read-only one.

What it must never show:
- **Clients never see this route or any of its data.** `lib/feature-tree.ts` scopes the `tasks` feature to `['team']`; every task API route is `isTahiAdmin`-gated; `/tasks` redirects a client org to `/overview`; `/tasks/[id]` redirects a signed-out user to `/sign-in` and otherwise resolves through the same feature gate. There used to be a client-facing branch of the old tasks page; it was deleted, not hidden, because every condition that could reach it was unreachable.
- **Client view (impersonation) leaves the same way a real client does.** The `tahi-impersonate-org` cookie bounces the previewer to `/overview`, so a team member previewing one client's portal can never see another client's tasks by opening this route in a second tab.
- **Team member access scoping is enforced on every read and write**, not just the page gate: `GET /api/admin/tasks`, the bulk route, the from-template route and the single-task PATCH/DELETE all call `resolveAccessScoping` or `requireAccessToOrg`. A scoped team member (rule 11 in CLAUDE.md) sees only the clients their `teamMemberAccess` rows grant, plus every task with `orgId IS NULL` (Tahi-internal work is visible to everyone by Decision 14). Deny-by-default: a team member with no access rule sees nothing client-linked.
- **A viewer-scoped impersonation is read-only.** When a super admin is impersonating a teammate whose every access rule is `role: 'viewer'`, the whole page (list, board, week, detail, quick-add, bulk bar) renders in a `readOnly` state: no PATCH, POST, DELETE fires, and the UI hides or disables every affordance that would attempt one (`readOnly` prop threaded through every leaf).
- **No Activity/audit trail exists for tasks.** `lib/audit.ts` records no task edits; the prototype's Activity card was deliberately not ported because there is nothing behind it. Do not design one without a schema decision first.
- **No public or print view.** Tasks are never shared outside the studio; there is no share link, no PDF, no email digest of a task.

## 2. Pages, sub pages and entry points

**`/tasks`**, the one canonical surface. Reached from the sidebar, from any task notification (which lands on `/tasks?task=<id>`), and from "Create request from task" / "AI: break work into tasks" cross-links on the Requests surface. Renders `<TasksContent>` inside a `Suspense` boundary because it reads `?task=` via `useSearchParams`.

Inside it, one page header (title "Tasks", subtitle above) with two header actions: **New task** (primary button) and an overflow menu (**AI: break work into tasks**, **New from template** grouped by template name, **Export CSV**). Below the header, a `RailLayout`: a left rail on desktop, a Filters bottom sheet on mobile (same `TasksRail` component, `touch` prop set), a view switcher, an active-filter chip strip, a search box, and the body region that swaps between the three views.

- **List** (default view). Quick-add bar at the top, a bulk-action bar when rows are selected, a `DataTable` with `expandedRowMode="rows"` so an expanded row's checklist renders as real `<tr>`s beneath it. Below `md` the table becomes stacked cards.
- **Board.** Four fixed columns off the status vocabulary (To Do, In Progress, Blocked, Done), built on the shared `KanbanBoard` (same component the Requests board uses). Each column has an inline "add a task" composer at its foot, suppressed on the Done column. Drag between columns re-writes status; dragging onto a card in a different column is read as a move onto that card's status (a "nest" gesture repurposed); dragging onto a card in the same column is a no-op (tasks carry no board ordering).
- **My week.** The viewer's own open plate (assigned to them, not done), grouped by day, drag-to-plan. Deliberately ignores the rail entirely: filters, saved views, search and sort are all inert while this view is on screen, and the rail shows a note explaining that inertness is removed from the UI copy (Liam's call, 2026-09-06), the inert controls themselves are the only signal now.

**`/tasks/[id]`**, not a page, a redirect shim. `getServerAuth` then `requirePageFeature('tasks')`, then `redirect('/tasks?task=<id>')`. Exists purely so notification links and old bookmarks land somewhere real. No design needed; nothing to review visually.

**Task detail**, a right-hand `SlideOver` (`maxWidth: 35rem`), opened by clicking any row/card, by a notification, or by `?task=<id>` on load; closed by clearing the query param. There is no separate detail page. Cards inside, top to bottom: status chip + overflow menu (Duplicate, Create request from task when eligible, Delete); tick + auto-growing title; meta chips (Level, Request reference, Priority, Due date, "Read-only" when impersonated); a linked-request banner when the task both has a request and is `client_task` level; description textarea; **Waiting on** (blockers) card; **Links** card (Level segmented control, Client picker, Request picker); **Details** card (Assignee, Due, Priority, Estimate); **Checklist** card (subtasks, add/tick/remove); **Time** card (`TimeCard`, shared with Requests, timer, manual log, entries). Footer: "Create request from task" / "Open #NNN" / Delete.

**New task dialog**, a centred `SlideOver`, opened from New task, from a board column's composer (skips the dialog, posts directly), or from New from template (pre-fills the template). Two internal views, switched by a toggle at the top: **Form** (every field the API takes, including AI field-prediction suggestions on title/priority/due once the title is long enough) and **AI** (the same wizard body as the standalone drawer, but handing its draft into the form fields instead of posting directly, "Draft with AI" is the hand-off action here, not "Create tasks").

**AI task wizard**, two mount points, one component. Standalone: a right-hand `SlideOver` opened from the header's overflow menu (context: the rail's client filter, if narrowed) or from a Requests-side "break into tasks" action (context: the source request, pre-seeded composer text). Embedded: `AiTaskWizardPanel`, the same body with no drawer chrome, inside the New task dialog's AI view. Chat transcript, a composer that grows 1 to 8 lines, a paperclip/drop-zone for a brief (txt/md/csv/json/pdf, size and page-count capped), and per-draft review cards (title, description, category, priority, estimate, due date, checklist, client and assignee name-matched against the loaded rosters) with an edit-in-place affordance before anything is created.

**Task templates**, not a page in this group; managed on `/settings` (Settings → task templates, admin-only, global or per-client copy-on-write). This group only consumes them: the header's "New from template" list and the New task dialog's template pre-fill. Note this cross-reference in the design so nobody designs template CRUD twice.

**Blocker picker**, an inline searchable menu inside the detail panel's Waiting on card, server-searched (task or request, excluding the loop candidate and anything already linked), debounced 250ms.

**Promote dialog**, a centred `SlideOver` reached from the detail panel's overflow menu or footer button ("Create request from task"), shown only when the task has a client, no linked request yet, and is not Tahi-internal. Two inputs: category (design/development/content/seo/strategy) and size (one day or less / multi-day).

## 3. States and variants

- **Loading (first paint).** `booting` gates on two fetches (the task list and the viewer's own team-member id), because "assigned to me" and the whole week plate are wrong until both land. List: its own row-skeleton (owns its loading UI). Board: a 4-pane pulse skeleton. My week: a 3-pane pulse skeleton. Rail counts and the toolbar total both read the skeleton state via a shared `loading` flag.
- **Loading (detail panel).** A task not present in the already-loaded list (a deep link from a notification) triggers a fallback single-task fetch; the panel shows "Loading this task…" only while that fetch is actually in flight, never indefinitely.
- **Empty, List, no filter active.** Leaf icon, "Nothing on the list", "Add the first one above, or turn a request into work.", New task button (hidden when read-only).
- **Empty, List, a filter/search/saved-view is active.** Leaf icon, "No tasks match", "Try clearing a filter or the search.", Clear filters button.
- **Empty, My week.** Leaf-style `EmptyState`, "A clear week", "Nothing open is assigned to you. Enjoy it, or pull something in from All tasks."
- **Empty, Board column.** Each column's own empty affordance is the inline composer itself (shared `KanbanBoard` behaviour); Done takes no new work and has no composer.
- **Error.** Every write (patch, create, delete, subtask, blocker, bulk, promote) rejects, rolls back its optimistic state, and toasts either the server's own sentence (blockers: "That would make a loop", "That link already exists") or a generic "That did not save. Try again." Deleting an id that turns out to be gone already settles quietly with no task and no error, not a spinner forever.
- **Read-only (viewer-scoped impersonation).** Every write control across all three views and the detail panel is disabled or hidden: no drag, no quick-add, no bulk bar action buttons fire, checklist tick/remove hidden, blocker remove hidden, header's New task/AI/templates hidden (Export CSV survives, since it reads only), footer Delete hidden, the detail panel prints a small "Read-only" eye chip in the meta row.
- **Member seat vs admin seat.** Not a separate visual mode: an admin (Tahi org) sees everything the access-scoping rules allow; a non-admin, non-scoped member sees an empty tasks list by design (deny-by-default) with the same "Nothing on the list" empty state, there is no distinct "you have no access" message today, which is worth a design decision (see Open Questions). A scoped member (project_manager / task_handler / viewer per `teamMemberAccess`) sees only their granted clients' tasks plus every `orgId IS NULL` row.
- **375px.** Rail becomes a Filters bottom sheet (`touch` variant of `TasksRail`, 44px targets throughout); List becomes stacked mobile cards instead of a table; Board and My week keep their column/day layout with horizontal scroll (`KanbanBoard` already owns this for Board); detail SlideOver goes full width.
- **768px.** Table stays a table (breakpoint is `md`, 48rem); rail controls shrink their min-height from 2.75rem to 2rem where marked.
- **Dark mode.** All styling is CSS custom properties (`var(--color-*)`, `var(--status-*)`), so dark mode should work by construction, but STATUS.md explicitly flags dark mode on the Board and the My week planner as **not yet exercised live**, this is a live-QA gap, not a known bug, and the design review should look hardest here.
- **Print/public.** Not applicable; there is no such view for this surface.
- **Task-linked-to-request banner.** Shown only inside the detail panel when `level === 'client_task'` and a request is linked: states plainly that the request carries the client conversation and this task is for internal follow-ups only.
- **Pending-level state (Links card).** Pressing Client or Internal on a task that has no client does not write immediately: the segmented control visually holds the pressed value, a live-region caption says "X work needs a client. Pick one below and it lands.", and the Client picker opens under the pointer. This is a genuine interaction state worth its own design frame, not a bug: it exists to avoid a flash-then-revert on an eventual 400.

## 4. Features and actions

### /tasks, List view

**Works today:** quick-add with natural-language parsing (`@Client`, a weekday or relative date word, `!priority` with `!high`/`!urgent`/`!medium`/`!low` all accepted, aliasing to the three-value scale), live parse-preview chips under the input; seven saved views with live counts (Assigned to me, Due this week, Overdue, Blocked, Client-linked, Internal, Done) plus All tasks; six filter dimensions (status, priority, level, client, assignee, due) each a searchable select where relevant; sort with a direction toggle across multiple keys, Done always sorting last; Save as default (browser-local, inherited from the Requests rail pattern); Clear filters; expand-per-row checklist with add/tick/remove; bulk bar (status, priority, assignee, due date) with an honest updated/failed count from the server; row tick toggles done/todo; row click opens the detail slide-over; Export CSV (BOM-prefixed, exports what is currently on screen, honouring the active filter/search).

**Exists but wrong or half-built:** none identified specific to List beyond the surface-wide items below (STATUS.md's "not exercised live yet" list covers List's bulk-complete and CSV as part of the roughly-a-dozen behaviours only proven in `e2e/tasks.spec.ts`, not on the deployed URL).

**Planned or missing:** (none List-specific found in TASKS.md beyond the general live-smoke debt below.)

### /tasks, Board view

**Works today:** four columns (To Do, In Progress, Blocked, Done) mapped straight off the status vocabulary; drag a card between columns to move it; drag onto another card reads as a move to that card's column; inline per-column composer (not on Done); read-only mode fully disables drag and composers.

**Exists but wrong or half-built:** **STATUS P3 / catalogue line 126**, a card in the SAME column as the one being dragged still lights up as a drop target. Cosmetic, lives inside the shared `KanbanBoard`, and also shows on the Requests board, so a fix there fixes both. Board drag itself is one of the roughly-dozen behaviours proven only in the local e2e harness, not yet smoked live on production.

**Planned or missing:** tasks carry no persisted board ordering (`tasks.position` is a track-queue field nothing on this surface reads or writes); inventing within-column ordering is a real feature, not a bug, and is explicitly out of scope until someone asks for it (documented in TASKS.md T2.5 notes as "still orphaned on purpose").

### /tasks, My week

**Works today:** the viewer's own open plate, grouped by day with a seven-cell strip summary; drag a task onto a day to plan it (writes `dueDate`); the rail is suppressed while this view is active and the count/search/filters/saved-view controls are inert by design; toggling done from this view.

**Exists but wrong or half-built:** **TP.3 (catalogue, TASKS.md "Tasks and requests polish")**, the planner shows a real week of dates, but a task can only ever be dropped onto ONE day (a single `dueDate`), never spread across multiple days it will actually take. Liam's ask is explicit: "a long or big task or request can be placed into MULTIPLE days (spanned across the days it will take), not just dropped on one due date." This needs a design pass first and probably a schema decision (a per-day allocation distinct from the single due date), it is the single largest open item in this whole group. My week drag is also one of the behaviours proven only in the e2e harness, not live-smoked yet.

**Planned or missing:** multi-day allocation itself (TP.3, "design first, then FE/BE").

### Task detail (slide-over)

**Works today:** inline edit of every field (title, description, status, priority, due date, estimate, assignee) with optimistic save and rollback; the three-way Level/Client/Request consistency model (`lib/task-consistency.ts`) that keeps a task's level, client link and request link from ever disagreeing, including the "ask for a client first" interaction described above; checklist add/tick/remove with a progress bar; blockers add/remove with server-side loop and duplicate detection and an honest server-authored error sentence; Duplicate (carries the checklist across); Delete (with a confirm, states the checklist and logged time go too); Create request from task (promote), gated to tasks that have a client, no linked request yet, and are not Tahi-internal; Time card (timer, manual entries) shared with Requests.

**Exists but wrong or half-built:** none found specific to the detail body's own logic; STATUS.md flags the timer, bulk-complete, promote and an AI-wizard run from inside a task's own flow among the roughly-dozen behaviours proven only in `e2e/tasks.spec.ts`, not yet live-smoked on production.

**Planned or missing:** **no Activity/history card** (T2.5 notes: "deliberately not ported... there is no per-task event stream in the schema and `lib/audit.ts` records no task edits; building one is a table plus a write on every mutation"), if this is wanted, it is a schema-and-backend task before it is a design task, mark any activity affordance a design proposes as "proposal". **No delivery-phase / schedule-row selector** on this surface (deliberately dropped from the port; the link still lives and is edited from the schedule detail's Linked work section instead, do not reintroduce a control here without a decision to move that editing surface). **No teammate-vs-owner subtitle variant** (there is no audience switch on this surface at all, unlike Requests).

### AI task wizard (both mounts)

**Works today (per TASKS.md LW.13-LW.19, merged f2c3182f and folded into this port):** rendered markdown (bold, short lists only, no raw markdown leaking into bubbles), an auto-growing composer (1 to 8 lines) with a 44px send target, every draft created in isolation rather than the model being trusted to file one bundle, canonical hours estimates that override anything the model proposes and a prompt that refuses timelines the actual scope cannot meet, client context reaching the prompt (org name, industry, website, brand, last five requests) with a which-brand question for a multi-org account, and file-brief support (txt/md/csv/json/pdf) with size and page caps enforced client-side before the round trip. Drafts resolve client and assignee names against the loaded rosters (exact match, then unique-prefix match; an ambiguous name resolves to nothing rather than guessing wrong).

**Exists but wrong or half-built:** none specific beyond the shared "AI wizard run" line item in STATUS.md's live-smoke debt (it has never been run against production, only against the local e2e harness).

**Planned or missing:** none found beyond ordinary live-verification debt.

### Templates (consumed here, managed in Settings)

**Works today:** New from template pre-fills the create dialog (name, type, default priority, description, checklist, estimate); global templates apply everywhere, per-client templates layer over them.

**Exists but wrong or half-built / planned:** nothing found in this group's scope; template CRUD lives on `/settings` and is out of this document's routes.

### Cross-cutting / whole-surface

**Works today:** the shared rail pattern (saved views + filters + sort + search + Save as default) matching Requests exactly per the design critic; CSV export with a UTF-8 BOM so Excel does not mangle a client name; notification deep links (`/tasks?task=<id>`) opening the right panel on load.

**Exists but wrong or half-built:** **STATUS P3 / TASKS.md T2.5**, the whole Definition of Done (CLAUDE.md rule 8, checks 4-7) is still open for this surface: `npm run build` has been run against a merged tree but the plan's own Slice 6 smoke list still names roughly a dozen behaviours (bulk complete, promote, the timer, an AI wizard run, Save as default surviving a reload, the CSV download, the board drag, the My week drag, the filter chip, the client-org redirect, and dark mode across all three views) that are proven only in `e2e/tasks.spec.ts` against a local harness, not live on the deployed URL. This is the single biggest "what is left" item for the whole group and is a QA/live-smoke task, not a design task, but the design review should treat anything it cannot verify from a screenshot (drag, timers, CSV) as unverifiable and say so rather than guessing it works.

**Planned or missing:** **TP.4, notifications page** (design first, then FE), an All notifications / Past notifications page behind the bell, described in TASKS.md as low priority and not part of this route group's pages, noted here only because the bell surfaces task notifications that deep-link into this surface. **Task calls have no surface**, the API and MCP tools exist (see Section 5) to attach a call (planning sync, review) to an internal task, but no card, button or dialog anywhere in the detail panel, list, board or My week offers it; this is not called out in TASKS.md either, so it reads as backend-only scaffolding waiting on a design decision rather than a known bug.

## 5. Data and integrations

- **Tables:** `tasks`, `taskSubtasks`, task-to-task and task-to-request blocker edges (via the polymorphic blocker tables in `lib/blockers.ts` / `lib/blockers-server.ts`), `teamMembers`, `teamMemberAccess` + `teamMemberAccessOrgs` (access scoping), `organisations` (client picker), `requests` (link/promote target), a template table behind `/api/admin/task-templates` (schema-defined, managed on Settings), `timeEntries` (Time card, shared with Requests).
- **API routes this group depends on:** `GET/POST /api/admin/tasks`, `GET/PATCH/DELETE /api/admin/tasks/[id]`, `PATCH /api/admin/tasks/bulk`, `POST /api/admin/tasks/from-template`, `POST /api/admin/tasks/[id]/promote`, `GET/POST /api/admin/tasks/[id]/subtasks`, `PATCH/DELETE /api/admin/tasks/[id]/subtasks/[subId]`, `GET/POST /api/admin/tasks/[id]/blockers`, `DELETE /api/admin/tasks/[id]/blockers/[linkId]`, `GET /api/admin/blockers/search`, `POST /api/admin/ai/task-wizard`, `GET /api/admin/task-templates`, `GET /api/admin/team-members`, `GET /api/admin/clients?status=active`, `GET /api/admin/requests?status=all&limit=500`, `GET /api/admin/profile` (resolves the viewer's own team-member id).
- **Route that exists but this surface does not use:** `GET/POST /api/admin/tasks/[id]/calls` (calls attached to an internal task, `lib/calls.ts`, `guardTask` access-scoped) has no caller anywhere in `components/tahi/tasks/*` or `tasks-content.tsx`; it is reachable only through the worker MCP tools (`create_task_call`, `list_task_calls`, `update_call`, `delete_lead_call`-style siblings) and has no design in this document or a TASKS.md line. There is also a legacy alias `GET/POST /api/admin/tasks/[id]/dependencies` (+ `DELETE .../dependencies/[depId]`) kept only so old MCP tool calls (`add_task_dependency` etc) and saved agent transcripts keep working through a deploy window; the live UI calls `/blockers` exclusively, so `/dependencies` is intentionally dead to this surface, not a gap.
- **Third parties:** the AI wizard calls Claude (Haiku-tier per `project_ai_integration.md`) through the task-wizard route; no Stripe, Xero, Slack, HubSpot or Mailerlite dependency on this surface at all.
- **What must be honest:** the rail's counts must always equal what each saved view actually renders (no view can show a 7 next to a list of 3, this is why the Blocked reading is deliberately wide everywhere except the Board column, which is deliberately narrow because it means the value a drop writes). Export CSV must export what is on screen, not the whole table, and must say so implicitly by matching the visible count. The "assigned to me" / My week reading must never render before the viewer's own team-member id has resolved (this is exactly why `booting` waits on both fetches), a confident zero here would be a lie. Bulk actions must report the real updated count from the server, not the number of ids sent, so a partially-scoped bulk edit cannot claim more than it did.

## 6. Design system contract

- **Primitives already in use and correctly applied:** `PageHeader` (title + subtitle + header actions slot), `RailLayout` (rail / rail-touch / switcher / chips / search / total), `DataTable` with `expandedRowMode="rows"` and a `mobileCard` fallback, `SlideOver` (right variant for detail, centre variant for the create dialog and the promote confirm), `ConfirmDialog` for delete, `KanbanBoard` (shared with Requests, including its 44px mobile targets and proxy scrollbar), `SidebarCard` for the detail panel's four cards, `InlineMenuField` / `InlineDateField` / `InlineNumberField` for in-place edits, `StatusChipSelect`, `SegmentedControl` (Level control, Promote size control), `Badge` (priority, level, status), `Avatar`, `TahiButton`, `BulkActionBar`, `Menu` (overflow actions), `TimeCard` (shared with Requests). Leaf radius (`--radius-leaf`) is used exactly once outside the header CTA and empty-state icon: the "linked to a request" callout banner in the detail panel, which is a deliberate restraint (CLAUDE.md: "not for every card").
- **What the existing design file (`tasks.jsx` + `tasks-data.jsx` + `tasks.css`) gets right:** the critic's Pass 3 verdict is SHIP, "matches Requests exactly", the same rail/table/board/menu classes are reused rather than reinvented, confirmed by inspection (the file composes off `window.RQ`'s shared icon/avatar/checkbox/toast kit and the Requests detail sheet's rail cards and inline editors, exactly mirroring how the live code shares `SidebarCard`, `InlineMenuField` and `KanbanBoard` with Requests). This is the one page in the whole catalogue where design and code are already this close; treat any review finding here as either cosmetic or a genuine live-behaviour gap, not a structural mismatch.
- **What the design must still change or verify:** **My week's real week-and-multi-day-allocation model (TP.3)** does not exist in the design file yet in the form Liam wants (spanning a task across several days), this needs a fresh design pass, not a port, before any FE/BE work starts. The **head-band / left-rail consistency pass (DL.2)** already wrote `tasks.jsx` into its target shape (one of the nine files patched 2026-09-12), so the rail should already read as one implementation with the other list-style pages (Requests, Clients, Time, Team, Leads, Deals, Calls), the design review should confirm this landed correctly rather than assume it. Dark mode on the Board and My week views has never been screenshotted against the live shell as far as STATUS.md records; treat it as unverified rather than passing.

## 8. Acceptance for the design review

1. At 1440, the rail (saved views, filters, sort) visually matches the Requests rail's spacing, band height and control sizing, same head-band, same `.lrail` family, not a near-miss.
2. At 375, the Filters control opens a bottom sheet (not a cramped inline rail), every control and option inside it is at least 44px tall, and the page has no horizontal scroll on List or My week (Board's own horizontal scroll is expected and fine).
3. The List empty state (no filter) shows the leaf icon, "Nothing on the list" copy and a New task CTA; the filtered empty state shows "No tasks match" and a Clear filters CTA, both present and distinguishable in the screenshot set, not the same frame relabelled.
4. The Board's four columns read as To Do / In Progress / Blocked / Done in that order, with the composer visible on every column except Done.
5. My week visibly ignores the rail: filters/sort/search read as inert (dimmed or disabled) while this view is the one on screen, per Liam's explicit instruction that no note is needed but the inertness itself must be legible.
6. The task detail slide-over's Level control shows the "waiting on a client" interaction state correctly: pressing Client or Internal on a clientless task holds the pill and visibly opens the client picker, rather than looking like a plain toggle.
7. Dark mode: List, Board and My week all render with correct contrast on status dots, priority badges, due-date chips and the Blocked dashed-ring tick, this is the one area STATUS.md says has never been live-verified, so treat any dark-mode screenshot here as the first real check, not a rubber stamp.
8. The AI wizard's chat bubbles render only bold text and short lists (no raw markdown asterisks or headers leaking through) in both the standalone drawer and the embedded New task dialog panel.
9. The "linked to a request" leaf-radius banner in the detail panel appears only when a `client_task`-level task has a linked request, and does not appear on Internal or Tahi-internal tasks even when they happen to have a request link.
10. No dead or decorative control exists on screen that does not map to a real API call: every button in the header's overflow menu, the bulk bar, and the detail panel's overflow menu must correspond to a route named in Section 5.
