## 1. Purpose and audiences

`/overview` is one file (`app/(dashboard)/overview/page.tsx`) that renders a different home component per resolved audience, decided by `OverviewHome` (`components/tahi/overview/overview-home.tsx`). This document covers only the studio side of that switch:

- **Owner** (`OwnerHome`): rendered when the resolved permission level is not `team_member`, i.e. `super_admin` or plain `admin` inside the Tahi org (`NEXT_PUBLIC_TAHI_ORG_ID`). Today that is Liam and Staci. Job: one glance at the whole studio, in this order: money coming in and owed, the daily brief and what needs a decision right now, cash and take-home, the pipeline ahead, what is in flight this week, client health and paper, and the growth engines (content, social, reviews, docs). It is the "studio ledger" STATUS.md and the catalogue both name as one of the two daily-trusted homes.
- **Teammate** ("My studio", `TeammateHome`): rendered when the resolved level is `team_member` (a scoped hire). Job: a personal work queue, not the studio's books. No currency anywhere on this home (`useOvFormat()` is deliberately never called). Sections: my open work, overdue/due-today/timer/replies vitals, needs-you (overdue task, next call, oldest reply), my day (my tasks, today's calls), waiting (client replies on my requests), my week (a live time-tracking card, studio docs).
- **Admin previewing a teammate** ("Act as" / "View as"): same `TeammateHome` component, forced `isReadOnly: true`. This is the one variant of this group with a known, documented gap: the member-scoped routes (`/api/admin/overview/me`, tasks-assignee=me, time?teamMemberId=me) still resolve to the ADMIN's own identity, not the previewed member's, so what Liam sees in preview is his own scoped data relabelled with the teammate's name, not what the hire actually sees (`overview-home.tsx:115-118`, TASKS T1.19).

What this group must never show:

- **No client data leaking into the studio's own view of itself.** This is a Tahi-internal surface; it aggregates across every client and must never scope down to "my org" the way the client home does. (The reverse leak, a client somehow landing on the owner/teammate layout, is prevented one level up in `OverviewHome`, which is client-home's contract, not this one's.)
- **No Messages surface or CTA anywhere on this home.** Messages is hidden platform-wide (Decision V1, TASKS.md, live since 2026-08-18); every card that used to point at `/messages` (owner "Unread messages", any dead pointer) has been rerouted to land on the actual request thread instead (CT.5, shipped). Nothing in a redesign of this page should reintroduce a Messages tile, tab or deep link.
- **No studio-wide financials or work leaking to a scoped teammate.** The teammate home must show only that member's own queue (their tasks, their calls, their replies, their time), never the owner's Books/Ahead/Clients/Growth zones. Today this boundary is enforced primarily by which HOME COMPONENT renders (`level === 'team_member'` branches to `TeammateHome`, never `OwnerHome`), but it is not purely a UI-only boundary as an earlier pass of this document claimed: both `/api/admin/overview` and `/api/admin/overview/wire` (default scope) DO call `resolvePermissions` + `can()` and omit the money-shaped fields (MRR, cash, runway, burn, AR aging, invoice totals gated on `financial_reports`/`invoices`; wire events gated on `financial_reports`/`clients`) when the caller's resolved access lacks the feature. What is NOT feature-gated on either route, and so would still leak to a scoped hire who called the endpoint directly: `/api/admin/overview`'s active-client count, open/in-progress request counts, the recent-requests list, and clients-by-plan/open-by-status buckets; and `/api/admin/overview/wire`'s non-money, non-client event sources (content, sales, ops). So the gap is real but narrower than "no per-route check at all": it is the non-financial studio-wide aggregates that remain unscoped, not the money figures. This is the general "deny by default" gap tracked at TASKS T1.15/T1.16/T1.18 (catalogue Batch F), not something specific to this page.
- **No fabricated numbers.** The owner home's code comments call this out explicitly: no invented "reach" stat on Social, no fabricated cash-flow monthly series where none exists (a horizon strip stands in), no forecast sparkline that is not backed by the real per-stage pipeline. Any redesign must preserve this: every card either shows a real, sourced figure or an honest empty state, never a placeholder number that looks real.
- **No super-admin-only surface leaking to a plain admin or a teammate.** There is no super-admin-only zone on this page today (Private mode / demo mode live elsewhere), so this is a forward-looking constraint only: if a future card is added that only Liam+Staci (super_admin) should see, it must gate on the resolved `super_admin` role, not organisation membership.

## 2. Pages, sub pages and entry points

This group has exactly one route and no sub-routes, dialogs or slide-overs of its own; every "Open" action on a card navigates AWAY to the owning page.

- **`/overview`**, the only URL. Entry points: the sidebar's first item for both audiences; the post-sign-in redirect target once onboarding/org resolution is done; `/continue` hands off here once a Clerk session resolves an org; any nav item's "home" breadcrumb.
- **Owner variant**, same URL, rendered when `level !== 'team_member'` and no impersonation is active. No query params of its own.
- **Teammate variant**, same URL, rendered when `level === 'team_member'`. No query params of its own.
- **Admin-previewing-teammate variant**, same URL, no query param of its own (corrected: not `?asMember=<id>` as an earlier pass assumed). Entry is the "View as" action on `/team` (`team-content.tsx`'s `setTeamMemberImpersonation`), which writes the previewed member's id, name and access rules to a per-tab sessionStorage record (`impersonation-banner.tsx`) and then plain-navigates to `/overview`. Client-side and per-tab only, admin-only; forces the teammate layout in read-only mode with the previewed member's name in the header.
- **In-page interactive surfaces (not separate pages, no URL state):**
  - **New menu** (owner and teammate): a small popover off the hero, not a dialog, "New request" / "Add client" / "Log time" (owner) or "New task" / "New request" / "Log time" (teammate). Disabled entirely when `isReadOnly`.
  - **Daily brief accordion** (owner only): three collapsible sections, Urgent today, This week before they bite, While you slept, plus a manual Refresh button that POSTs `/api/admin/overview/brief/refresh?force=1` and revalidates. Not a dialog; state (`open`, `refreshing`) is local to the card.
  - **Every card's title-link and every row** is a `go(id)` call that pushes a real dashboard route (e.g. "Open books" -> `/financial-reports`, a Hot leads row -> `/leads`, a Today's calls "Join" button -> `window.open(meetingUrl)`). None of these are sub pages of `/overview`; they are the entry points FROM `/overview` into every other studio surface. Listing them because a design review needs to know every card is a doorway, not a dead end.

There are no modals, slide-overs or tabs native to this page. If a redesign introduces one (e.g. a "See all" drill-in for a card), that is new scope and should be called out as a proposal, not assumed.

One line each, owner then teammate.

- **Owner, error:** only one card distinguishes a fetch error from "still loading" today, Client replies waiting shows "Could not load client replies. Try again shortly." when the resource errors with no cached data. Every other card on this page has no error state of its own; a failed fetch just leaves it in the loading shimmer indefinitely (a design gap worth flagging in section 6, not a variant to design around as normal).
- **Owner, read-only (previewing a client, "money read-only"):** N/A, the owner home never renders in read-only mode; only the client and teammate homes do. (Owner-as-admin previewing a client renders `ClientHome`, out of scope for this group.)
- **Owner, member seat vs owner seat:** N/A for this component, the owner home only ever renders for `admin`/`super_admin` resolved levels, so there is no "member seat" variant of `OwnerHome` to design.
- **Owner, 375px:** the grid is a CSS `container-type: inline-size` layout (`.ov` sets it), so breakpoints are container queries on the `.ov` element's own width, not the viewport: `@container (max-width: 66rem)` and `@container (max-width: 46rem)` collapse the 12-column card grid, the vitals strip, and the two-lane blocks to single columns. At an actual 375px viewport this container is well under 46rem, so every card stacks to one column, the vitals strip wraps to roughly 45%-wide pairs (`.ov-vital{flex:1 1 45%}`), and zones collapse their 2-column label+content grid to one column (`.ov-zone`). Touch targets: `@media (pointer:coarse)` rules exist in the stylesheet (two blocks), which is the right mechanism, but this has not been walked row-by-row against the 44px rule in this pass, flag for the reviewer to check the Daily brief accordion header, the New-menu trigger and the card "more" buttons specifically, since those are the smallest hit targets on the page.
- **Owner, 768px:** falls inside the `@container (max-width: 66rem)` band, one step short of full single-column; expect two-column card rows rather than the desktop's fuller 12-column grid. Not separately verified live.
- **Owner, dark mode:** every colour on the page is either a `var(--...)` token or one of a short list of documented inline hexes (status dots, domain-wire dots, chart series colours, CLAUDE rule 2's allowed exception for chart/status inks). No component-level dark override exists or should be needed; this page inherits the global `.dark` class. Not separately live-verified per STATUS.md ("Overview homes... owner + client verified live July; teammate home never visually verified", dark mode specifically has not been confirmed since).
- **Owner, print or public:** not applicable; this is an authenticated internal surface with no print stylesheet or public variant.
- **Teammate, loading:** same per-card independent skeletons (`RowsSkeleton`, inline `Skel` spans for the hero/vitals numbers) rather than one blocking spinner.
- **Teammate, empty (exact copy):** "Nothing assigned to you right now." (My work); "No calls on your calendar today." (Today's calls); "No client replies are waiting on you." (Client replies waiting); "No docs in the hub yet." (Studio docs); "All quiet." / "Nothing is waiting on you right now." (Needs-you quiet state); "Nothing on your plate right now" (hero sub when open work is zero); "Nothing is tracking right now." (Time tracking, no active timer).
- **Teammate, error:** no distinct error copy anywhere on this home; every card's failed-fetch state is indistinguishable from "still loading" (same gap as the owner home, worse here because there is no error-aware card at all on this variant).
- **Teammate, read-only (admin previewing a teammate):** `data-ro="1"` on the root disables the New-menu and every write affordance via CSS; the header carries the previewed member's name. Known bug (not a variant to design differently, a correctness gap to flag): every "me"-scoped data fetch still answers for the ADMIN, not the previewed member, so the numbers shown are wrong for this mode today (T1.19).

## 4. Features and actions

### Owner home

**Works today:**
- Live MRR hero with a 12-month revenue spark line and month-over-month delta, suppressed when the current month has no invoiced revenue yet (avoids a misleading "-100%").
- Vitals strip: Cash (with runway-horizon micro-bar), Owed (aged AR bar, separates drafts from owed), Clients (plan-split bar), Open (building/review/queued split), all real, all honestly muted when data is absent.
- Needs-you block: ranks an overdue invoice, an imminent call (within 2 hours), and off-track engagements by a severity score, surfaces the single most urgent one.
- Daily brief: three-section accordion (urgent / this week / while you slept), server-cached once per morning, manual force-refresh, "Updated Nh ago" freshness label.
- Books zone: Take-home gauge with reserve pots, Cash runway with a 12-month horizon strip, Cash-flow ribbon (12-month net), Receivables (aged AR bar).
- Ahead zone: Pipeline ahead (weighted total, open-deal count, closing-this-month count, per-stage bars sourced from the real forecast, never contradicting itself because the headline and bars share one payload), Studio capacity (gauge + per-member utilisation bars), Hot leads (score-sorted, Hot/Warm chips), Proposals live (status chips, newest-shared-first).
- Work zone: In the studio (recent requests, status dot + label), Today's calls (Join button appears only inside a live window), Client replies waiting (routes to the actual request thread, not the hidden Messages page, a deliberate fix, see CT.5/CT.F), Worklog this week (tracked/billable%/avg-per-person + per-member bars).
- Clients zone: Retainer health (healthy/at-risk/attention buckets, flags the two riskiest first), Contracts (active count, renewing-within-30-days count, rows sorted renewal-soonest-first).
- Growth zone: Content engine (in-draft/awaiting-review/ready counts + 8-week cadence spark), Social cadence (posts/week + 8-week cadence spark, or a "Connect Buffer" prompt when unconfigured), Reviews & case studies (active outreach only), Docs hub (three most recently edited pages).
- The Wire: a cross-dashboard event ticker across the masthead.

**Exists but wrong or half-built:**
- **T2.7, Daily-briefing dedup** (open, TASKS.md, catalogue effort 1d): the home's Daily Brief card and the nav-bar briefing popover are two surfaces summarising overlapping ground with no shared source of truth; Liam's own framing (2026-08-18) is "one source of truth, one refresh cycle... nav popover summarises, home card expands." This is the one item the catalogue still lists as open for `/overview` as of 2026-09-13.

- **No error state on 20 of the page's ~21 cards.** Only Client replies waiting distinguishes "failed to load" from "still loading." ## 5. Data and integrations

- **`GET /api/admin/overview`**, the owner masthead + KPI payload: active clients, open/in-progress request counts, outstanding/draft/overdue invoice totals (NZD), MRR and its month-over-month delta, recent requests, 12-month monthly revenue, cash + runway + burn, AR aging buckets with the single oldest overdue invoice, open-by-status counts, clients-by-plan counts, active timer label. Reads `organisations`, `requests`, `invoices`, `exchangeRates` (via `lib/currency.ts` for FX), and the aggregation helpers in `lib/overview-aggregates.ts`. Gated `isTahiAdmin`, plus feature-level omission of MRR/cash/runway/burn/AR-aging/invoice totals via `resolvePermissions`/`can(access, 'financial_reports' | 'invoices')`; request/client counts and the recent-requests list are not similarly gated (see section 1).
- **`GET /api/admin/overview/wire`** and **`GET /api/admin/overview/wire?scope=me`**, the cross-dashboard event ticker, merged from multiple domains (content, social, sales, money, client, ops) via `lib/overview-wire.ts`; every source is individually try/caught so one missing table or column can never 500 the whole ticker. The default-scope route omits money events without `financial_reports` and client events without `clients` (`resolvePermissions`/`can()`, mirrors the base overview route); content/sales/ops events are not similarly feature-gated.
- **`GET /api/admin/overview/brief`** and **`POST /api/admin/overview/brief/refresh?force=1`**, the owner Daily Brief, computed once per NZ morning (cron target `overview-brief`, self-gated to NZ hours 7-8 and a >3h-stale cache) or on-demand via the manual Refresh button; cached in `settings` under `overview_brief_latest`, keyed per resolved-access fingerprint (`lib/brief-cache-key.ts`) so two differently-scoped viewers never share a stale brief. Uses `lib/access-scoping.ts` and `lib/permissions.ts` (`resolvePermissions`, `can`).
- **`GET /api/admin/overview/me`**, the teammate Hero/Vitals aggregate, resolved off `teamMembers.clerkUserId = auth.userId`; returns honest zeros/null (not studio-wide numbers) when the caller has no team_members row.
- **`GET /api/admin/overview/replies-waiting?scope=me`** (both homes use this, owner unscoped for its own card, teammate with `scope=me`), request threads where the last visible message was client-authored, 60-day lookback, capped at 12, reads `messages`/`requests`/`organisations`.
- Card-level dependents used only by the owner home: `/api/admin/financial-reports/summary` (Take-home), `/api/admin/reports/cash-flow-forecast` (Xero-derived), `/api/admin/deals` + `/api/admin/reports/pipeline-forecast` (Pipeline ahead, deliberately reads the forecast for money/bars and deals only for expected-close-date filtering, so the headline can never contradict the bars), `/api/admin/pipeline/capacity` (Studio capacity), `/api/admin/leads?status=new` (Hot leads), `/api/admin/proposals` (Proposals live), `/api/admin/reports/worklog?range=week` (Worklog), `/api/admin/reports/retainer-health` (Retainer health, feeds off `organisations.healthStatus` and a churn-risk score), `/api/admin/contracts` (Contracts), `/api/admin/content/drafts` + `/api/admin/content/schedule` (Content engine, ties to Content Studio / Slice work), `/api/admin/integrations/buffer/status` + `/api/admin/integrations/buffer/posts` (Social cadence, third-party Buffer), `/api/admin/reviews` (Reviews & case studies, note `/reviews` itself is flagged elsewhere in the catalogue as having a broken Send button and a dead review-link route; this card only reads status, so it is not directly affected, but any "go to reviews" click lands on that known-broken page), `/api/admin/docs` (Docs hub).
- Card-level dependents used only by the teammate home: `/api/admin/tasks?assignee=me`, `/api/admin/discovery-calls/upcoming?limit=8&includePast=1`, `/api/admin/time?teamMemberId=me&dateFrom=...&dateTo=...` (called twice, for the week and for today), `/api/admin/docs` (shared with the owner card, unscoped by org because `docPages` has no org column).
- Third parties in the data path: **Xero** (cash, runway, cash-flow forecast, AR aging all ultimately trace to Xero-synced balances per `project_bank_truth_architecture`, Airwallex is the cash source of truth, Xero the ledger, per the user's own memory), **Buffer** (Social cadence), the internal AI briefing pipeline (Daily brief content generation, not a separate vendor).
- **Must stay honest:** no card may show a number with no real source (already the stated design intent, see section 1); no card may link anywhere that 404s or silently no-ops, the "go to reviews" and "go to messages" classes of dead link are exactly what CT.5/CT.F closed for this page and a redesign must not reopen them; the New-menu items and every "Open"/"Join"/link action must resolve to a route that exists and does the thing its label promises.
- **New-menu items under-deliver their own label today (not previously called out):** owner "New request" (`go('requests')`) and "Add client" (`go('clients')`), and teammate "New task" (`go('tasks')`), all navigate to the plain list page, not to that page with its create dialog pre-opened. `request-list.tsx` supports auto-opening its new-request dialog via a `?new=1` query param (already used by seven other client-home affordances per T2.2's own note), but `overview-home.tsx`'s `go()` never appends it, and `/clients` and `/tasks` have no equivalent `?new=1` handling in their list components at all (checked: no match for that param in either). ## 6. Design system contract
