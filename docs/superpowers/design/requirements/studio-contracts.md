# Design requirements: studio-contracts

Group: studio-contracts (audience: studio only). Routes: `/contracts`, `/contracts/[id]` (Body, Signers, Activity), `/contracts/templates`.
Prepared 2026-09-13 for the Claude Design pass. Source: CLAUDE.md, STATUS.md, `docs/superpowers/plans/2026-09-13-page-catalogue.md`, `docs/superpowers/plans/2026-09-13-design-review-checklist.md`, TASKS.md, live code (`app/(dashboard)/contracts/**`, `app/api/admin/contracts/**`, `app/api/public/contracts/**`, `lib/contract-chain.ts`, `lib/contract-signature-notify.ts`, `lib/contract-signed-artifact.ts`, `lib/contract-signed-pdf.ts`, `lib/contract-fully-signed-emails.ts`), and `sales-artifacts.jsx` in the Claude Design project (57bf60cf-5e6d-450f-9e2f-e25c8d12fd66).

## 1. Purpose and audiences

Contracts is the studio's e-signature and legal-document surface: NDAs, SLAs, MSAs, SOWs, MOUs and other agreements, written once as reusable templates, raised per client, sent for signature over a tokenised public link, and tracked through a tamper-evident hash chain to a fully executed, R2-stored PDF. It answers three questions for whoever opens it: what is out for signature and stalling, what still needs signers or filled-in terms, and can we prove, forensically, what was signed and when.

Audiences:
- **Liam and Staci (super admin / owner).** Full access to every contract regardless of `teamMemberAccess` scoping.
- **A scoped Tahi team member** granted the `contracts` feature (`lib/feature-tree.ts` registers `contracts` with `route: '/contracts'`). Every admin route under `app/api/admin/contracts` calls `requireArtifactAccess` or `requireContractAccess` (`app/api/admin/_sales-access/artifact-scope.ts`), which resolves the contract's owning org (direct `orgId`, or the org behind a linked `dealId`) and checks it against the caller's `teamMemberAccess` scope before returning or mutating anything. A scoped member with no rule at all sees nothing (`scope.kind === 'none'` returns `{ items: [] }`).
- **Nobody else.** This is never a client-facing page inside the dashboard shell. `app/(dashboard)/contracts/page.tsx` redirects to `/requests` whenever `!isAdmin` OR `isPreviewingClient` is true, with an explicit comment: an admin previewing "what a client sees" must not be able to leak one client's contract work into another client's preview. `lib/feature-tree.ts` lists `contracts` with `appliesTo: ['team', 'client']`, but that flag currently has no live effect for clients on this route, the hard redirect fires first, for every client, regardless of what `feature_visibility` says. This is a real inconsistency worth resolving (see section 4 and section 7): either the tree entry is stale metadata that should read `['team']` only, or a client-facing read-only Contracts view was once planned and never built. Treat it as `team`-only for this design pass; do not design a client variant.
- The **actual client-facing surface** for a contract is a completely different route family, `/p/contract/[token]` and `/p/contract/[token]/sign/[signerId]`, which is out of scope for this group (studio only). Section 5 notes it only as a downstream dependency.

What it must never show:
- One client's contract, name, body, signer list or hash chain to a team member scoped to a different client, or to nobody's scope at all. Enforced server-side on every list and detail route (section 5).
- A client, ever, inside `/contracts`, `/contracts/[id]` or `/contracts/templates`, the page-level redirect above, both for a real client session and for the admin-as-client preview cookie.
- A super-admin-only sub-area does not exist on this surface: the only privilege split is scoped-member-with-a-rule versus everyone else (deny by default for a member with no rule).
- The contract body, once a signature exists, must never render as editable, and the API backs this: `PATCH /api/admin/contracts/[id]` refuses any `bodyHtml` or `variableValues` change once `status !== 'draft'`, returning 400 "A sent contract cannot be edited. Revoke it first."

## 2. Pages, sub pages and entry points

- **`/contracts`** (list). Reached from the sidebar "Sales" group and by deep link. Server-gated by the admin/preview redirect above, then `requirePageFeature('contracts')`. Renders `PageHeader` ("Contracts"), a `FilterBar` with two pinned multiselect chips (Status, Type) plus a free-text search box, and a `DataTable` inside a `Card`. Header actions: Refresh, a link to `/contracts/templates`, and "New contract".
- **New contract slide-over.** Not a route; `showCreate` local state opens a `SlideOver` (48rem) with Name, Type, Organisation, an optional "From template" select, and (only when no template is picked) an inline `TiptapDocEditor` for a custom body. Submits `POST /api/admin/contracts`, then the caller navigates to `/contracts/[new id]`.
- **Delete confirm.** Not a route; a `ConfirmDialog` triggered from a row's overflow menu or the create failure path. Calls `DELETE /api/admin/contracts/[id]`.
- **Row overflow menu** (per row, not a page): Open (navigates to `/contracts/[id]`), Public viewer (only when `publicShareToken` exists, opens `/p/contract/[token]` in a new tab), Delete.
- **`/contracts/[id]`** (detail, the builder). Reached by clicking a row, by "New contract" completing, or by deep link. Renders a `BuilderShell` with a sticky header, a centre editor pane, and a right rail. Three nav sections inside `BuilderNavGroup`, switched by local `activeView` state (no URL change, no `?tab=` query param):
  - **Body.** The contract terms. A `TiptapDocEditor` when `status === 'draft'`; a read-only rendered view once locked (signed, cancelled or expired), with the hint "Locked (signed)".
  - **Signers.** List of `AddSignerDialog`-created signer rows (role, name, email, position, status, per-signer public sign link with Copy, Resend and Remove actions), an "Add a signer" affordance, and a signed-count summary. Remove is only offered per-card while that signer is still `pending` and the contract is unlocked; it calls `DELETE /api/admin/contracts/[id]/signers/[signerId]`.
  - **Activity.** The audit trail: contract created / sent / each signature (with per-signature `HashRow` for `chainHash`, click to expand, click to copy) / fully signed, plus the `finalHash` fingerprint once every signer has signed.
- **Right rail sections**, present regardless of the active nav tab: "Send for signature" (Email all pending / Customise + send, opening the `EmailShareModal`), "Signed PDF" (Download / Resend, only once `status === 'signed'`), "Public link" (share URL with Copy/Open, plus Rotate and Revoke while unlocked, plus "Generate share link" when none exists yet), "Linked to" (`LinkedToPanel` for org/deal/proposal), and "Details" (Type select, Expires date, Created/Sent/Signed read-only stamps).
- **Add signer dialog.** Not a route; opened from the Signers rail button. Role (a fixed `<select>` of Tahi Studio / Client / Other, backing a `'tahi' | 'client' | 'other'` value, not free text), Name, Email.
- **Revoke confirm.** Not a route; `ConfirmDialog` from the Public link rail section. Calls `DELETE /api/admin/contracts/[id]/send`, which resets every signer to pending, deletes every signature, clears the token and `finalHash`, and writes an `auditLog` row of exactly what was discarded before deleting it.
- **Delete confirm** (detail page's own, distinct copy from the list's). `ConfirmDialog`, "Permanently removes the contract, all signers, and all signature records. Cannot be undone."
- **Save-as-template prompt.** Not a route; a `PromptDialog` (name only) reachable from the builder's more-menu equivalent, posts to `/api/admin/contracts/templates` with the current body.
- **`/contracts/templates`** (template library). Reached from the "Templates" button on `/contracts`'s header, or by deep link. A "Back to contracts" link, `PageHeader` ("Contract templates"), `FilterBar` (Type chip + search), and a `DataTable` (Name + description, Type badge, Updated date) inside a `Card`.
- **New template slide-over / edit template slide-over.** Not routes; local `showCreate` / `editing` state opens a `SlideOver` with Name, Type, Description, and a `TiptapDocEditor` body. Same shell for create and edit.
- **Delete template confirm.** Not a route; `ConfirmDialog`, calls `DELETE /api/admin/contracts/templates/[id]`.

## 3. States and variants

- **`/contracts` loading.** `DataTable`'s built-in skeleton rows while `/api/admin/contracts`, `/api/admin/clients` and `/api/admin/contracts/templates` are in flight (three parallel SWR fetches).
- **`/contracts` empty, none exist.** `EmptyState`: FileSignature icon, "No contracts yet", "Create your first contract. Start from a template or paste in custom terms.", CTA "New contract".
- **`/contracts` empty, filtered to zero.** `EmptyState`: "No matches", "Try clearing a filter or adjusting your search.", no CTA.
- **`/contracts` error.** Not modelled: `contractsData?.items ?? []` silently falls back to empty, so a failed fetch renders identically to the true-empty state. A proposal for this pass (see section 4).
- **`/contracts` scoped member with zero access.** `scope.kind === 'none'` returns `{ items: [] }`, which renders as the "No contracts yet" empty state even when contracts genuinely exist elsewhere in the system. No banner distinguishes "you have no access" from "there is truly nothing yet."
- **`/contracts/[id]` body, unsent (draft).** Editable `TiptapDocEditor`. No lock pill.
- **`/contracts/[id]` body, locked (signed / cancelled / expired).** Read-only render, "Locked (signed)" hint on the nav item, a lock icon somewhere the design should place deliberately (the live rail hint text is the only current cue).
- **`/contracts/[id]` signers, none added.** "Add at least one signer to enable signing." copy in the Send-for-signature rail; the Signers pane itself needs its own empty affordance (current live copy is terse, no icon-led `EmptyState`).
- **`/contracts/[id]` signers, some pending.** "Email all pending (n)" primary + "Customise + send" secondary in the rail.
- **`/contracts/[id]` signers, all signed but contract not yet flipped.** Should not be reachable (the sign route flips status to `signed` the instant the last pending signer signs, in the same transaction as the signature insert), flag as a defensive-only state, not a designed one.
- **`/contracts/[id]` fully signed.** Rail shows "Signed PDF" section (Download / Resend), Public link section loses Rotate/Revoke (both hidden once `isLocked`), Body and Signers both render read-only.
- **`/contracts/[id]` cancelled or expired.** Same lock behaviour as signed, but the Send-for-signature rail copy reads "Cancelled. No further signing." or "Expired. No further signing." instead of "Fully signed."
- **`/contracts/[id]` no public link yet.** Public link rail shows "Generate a public link to share the contract for signing. Emails auto-mint one for you." plus a manual "Generate share link" button.
- **`/contracts/templates` loading / empty / filtered-empty.** Same three-state shape as `/contracts`, not yet audited line by line for exact copy parity, treat as needing the same design attention as the list page rather than assuming it is already right.
- **Read-only Client view.** Structurally impossible on every page in this group: all three routes redirect before rendering whenever the caller is not `isAdmin`, or is an admin under `isPreviewingClient`. There is nothing to design for a client here.
- **Member seat versus admin seat.** Same UI, fewer or zero rows for a scoped member with a narrower `teamMemberAccess` rule; admin (or a member with `scopeType: 'all_clients'`) sees everything. No UI signal today distinguishes "this is your actual full list" from "this is filtered by your access", worth a design decision (section 7).
- **375px.** Not verified live on any of the three pages. `contracts-content.tsx` and `templates-content.tsx` both use the shared `DataTable`/`FilterBar` components that carry a documented mobile-card fallback pattern elsewhere in the app, but this group's specific mobile behaviour has not been screenshotted. The builder (`contract-detail.tsx`) uses `BuilderEditorShell`/`builderRailWide` styles shared with the proposal and schedule editors, whose Pass 3 critic verdict explicitly flags narrow-width problems on siblings (gantt pane, package tabs), the contract editor's own narrow-width behaviour (rail stacking, outline collapse) has not been separately verified.
- **768px.** Not verified live on any of the three pages.
- **Dark mode.** Not verified live. All three pages use `var(--color-*)` token references throughout rather than hardcoded hex (confirmed by reading every inline style block in `contracts-content.tsx`, `templates-content.tsx` and `contract-detail.tsx`), so they should inherit dark mode correctly by construction, but none has been eyeballed with `.dark` applied.
- **Print or public.** Not applicable to this group directly, `/contracts/[id]` is the studio editor, not the document the client reads. The client-facing print-like artefact is `/p/contract/[token]`, a separate route family outside this group's scope, though its public layout (`app/p/layout.tsx`) is worth naming here as a dependency: it strips any `.dark` class the visitor's browser carries from a previous dashboard session, on mount, for the whole `/p/*` subtree, so a contract signer never inherits the studio's dark-mode preference.

## 4. Features and actions

### `/contracts` (list)

**Works today:**
- List, search (name / org name / type), two pinned filter chips (status, type), sortable columns (Name, Type, Org, Status, Sent, Expiry), default sort by Sent desc.
- New contract from a template (with `{{variable}}` substitution server-side) or a custom pasted body, optional initial org link, optional seeded signers.
- Row actions: Open, Public viewer (new tab), Delete (cascades to signers and signatures via FK, confirmed by dialog copy).
- Per-org access scoping on the list query itself (`scopedOrgIds`, `filterArtifactsByScope`), not just a client-side filter.
- Signer progress (`signedCount` / `totalSigners`) computed server-side in one grouped query, not N+1, surfaced per row via the design's planned `SignProgress` component (not yet wired into the live list's columns, see "half built" below).

**Exists but wrong or half built:**
- **Global command-palette search reads a dead legacy table.** `app/api/admin/search/route.ts` queries `schema.contracts` (the old, unused table), not `schema.contractDocuments` (the real one every contract page and API route actually uses). A contract created today is invisible to the app-wide search even though it is fully visible on `/contracts` itself. TASKS T3.9 ("search reads contract_documents") names this; confirmed still open in code as of this pass.
- **The list has no `SignProgress` column.** The design's Contracts list (`sales-artifacts.jsx`, section "3. Contracts list") shows a `SignProgress` cell per row; the live `DataTable` columns are Name, Type, Org, Status, Sent, Expiry only, no at-a-glance "2 of 3 signed" signal in the table itself, even though the API already returns `signedCount`/`totalSigners` per contract.
- **No "stalled" surfacing on the list.** The design's Nudge banner ("X has been out for signature for N days, waiting on Y") and its "Chase list" saved view have no live equivalent; a contract that has sat unsigned for weeks looks identical to one sent yesterday.

**Planned or missing:**
- A left-rail saved-views pattern (All / Out to sign / Chase list / Unfilled slots / Drafts / Fully signed / Closed / Mine) per AR.5's "filters in a left rail on every list page" rule and the design file. Proposal: port this rail to replace or augment the current two FilterBar chips, consistent with how Requests and Tasks already do it.
- A `HeadBand` KPI strip (signatures due, slots unfilled, fully signed, next to expire), proposal, matches the design file, no backlog id found beyond the general AR.5/port-status entries.
- Row-level "Chase the pending signer" and "Cancel contract" actions distinct from "Delete", the live page only has Delete; "Cancel" (which the design treats as a terminal, on-the-record state distinct from destructive deletion) has no dedicated button or endpoint anywhere in the product. Note the generic `PATCH /api/admin/contracts/[id]` already types and accepts `status: 'cancelled'` in its request body and would persist it if sent, so the backend primitive half-exists; no caller in the codebase ever sends that value. This is a real gap: the enum has a `cancelled` state the product never reaches through any button, only through a request nobody issues.
- An explicit error state distinct from the empty state (section 3).

### `/contracts/[id]` (Body, Signers, Activity)

**Works today:**
- Three-section builder (Body / Signers / Activity) over a `BuilderShell`, matching the Proposals/Schedules editor family's shell pattern.
- Body edit while draft, hard-locked (API-enforced, not just UI-hidden) once sent.
- Per-signer add, direct remove (`DELETE /api/admin/contracts/[id]/signers/[signerId]`, gated in the UI to pending-and-unlocked signers only, no gate on the API side beyond the standard access check), copy link, resend signing email.
- "Send for signature" (mints/reuses a public token, flips `draft` → `sent`) and "Customise + send" (opens `EmailShareModal` for CC/BCC/subject/message) both hit `POST /api/admin/contracts/[id]/email`, which goes through the single delivery gate (`lib/email-delivery.ts`) so the `tahi.studio` allowlist applies and a held-back recipient reports as `suppressed` rather than falsely "sent."
- Tamper-evident hash chain: `chainHash = sha256(prevChainHash | signerId | signatureDataUrl | timestamp | bodyHash)`, `bodyHash` folded in at time of signing so a body edit after any signature is independently detectable (`lib/contract-chain.ts#bodyMatchesSignedHash`) even without keeping the old body text anywhere else. `finalHash` recorded once every signer has signed.
- Signed PDF persisted to R2 (`contracts/{contractId}/signed.pdf`) the moment it is built, not just attached to a fire-and-forget email; re-servable from the admin Download button and re-emailable from the Resend button, with best-effort regenerate-and-backfill for any contract signed before this existed or whose object has since gone missing from R2 (`lib/contract-signed-artifact.ts`).
- Every signature, partial or final, notifies the studio: a bell to every team member (`notifyAllAdmins`), a deal activity row when linked to a deal, and (for a partial signature only, since the final one gets its own richer email) a covering email through the same delivery gate (`lib/contract-signature-notify.ts`). This closes the "T3.3 close the accept/sign loop" and "notify on every signature, not only the last" items from TASKS/STATUS; both read as shipped in code (STATUS's Catalogue Batch C4, migration 0099).
- Revoke genuinely undoes state rather than just relabelling it: every non-pending signer goes back to pending, every signature row is deleted, the discarded signature and signer ids are written to `auditLog` before deletion (the only forensic trail once they're gone), and the document returns to `draft` with token/dates/`finalHash` all cleared. This closes TASKS T3.7's "fix revoke-resets-partially-signed."
- Save current body as a reusable template.
- Re-linking a contract's org or deal is itself access-checked against the target, so a scoped member cannot move a contract into or out of an org outside their scope.
- Activity log on deal link/unlink, written as `activities` rows so the deal's own timeline stays complete.

**Exists but wrong or half built:**
- **"Route contract-signed emails through the single `RESEND_FROM_EMAIL` chokepoint"** (catalogue functionality table, source CT.F). Reading the code: `lib/contract-fully-signed-emails.ts` and `lib/contract-signature-notify.ts` both already call `emailFromAddress()` from `lib/email-from.ts` for the actual `from:` header on every send; the only bare `FROM_NAME = 'Liam Miller'` constant in that file is written into an `auditLog` metadata field, not used as a send header. This item may already be resolved and the catalogue stale, flag it for a quick live verify rather than treating it as still-open work.
- **Signature pad has no resize/orientation handling.** `SignaturePad` in `app/p/contract/[token]/contract-viewer.tsx` sizes its canvas once on mount (`useEffect` reading `getBoundingClientRect` and `devicePixelRatio`, no resize listener, no orientation-change listener). A signer who rotates their phone mid-signature gets a misaligned canvas. This is on the public sign page, not the studio detail page, but it is a direct dependency of this group's "Send for signature" flow and is named in TASKS T3.5 and T3.10.
- **`/p/contract` viewer is still the older deliverable kit, not the new Claude Design `sales-artifacts-kit.jsx` viewer.** Out of this group's page list but a direct downstream dependency: every "Public link" and "Send for signature" action in this group's UI points at a viewer this design pass does not cover.
- **Template auto-save-as-template 400 bug** named in TASKS T3.9 ("save-as-template 400"), not independently re-verified in this pass; treat as still open per the backlog.
- **No inline preview of what the signer sees**, unlike the design's `PreviewPane` (phone/desktop toggle, "The signing page" label, live-rendered body with variables filled) sitting beside the editor at all times. The live builder only offers "Public viewer" as an external new-tab link from the list row or the rail, never an in-editor preview.

**Planned or missing:**
- A **Variables/Slots** nav section, separate from Body, so an admin can see and fill every `{{variable}}` in one place with a "N of M filled" completion count, rather than hunting through prose for double-braced placeholders. This exists in the design file (`ContractVars`, outline item "Slots") and has no live equivalent at all, `/contracts/[id]` today has no dedicated variables view; filling slots happens inline while editing the body. Proposal, tracks the design file's own new work, not a numbered backlog item found in TASKS as of this pass.
- An **Analytics/Reading** nav section for the contract's own view count and reading events, mirroring what Proposals already surfaces. Proposal, same status as above.
- A distinct **Cancel** action/state (see list section above) with its own confirm copy, separate from Delete and from Revoke.
- T3.9's small-fix batch items that touch this detail page specifically: `alert()`-to-toast (verify whether any remain on this page specifically, most `alert()` usage flagged by the catalogue is in the public viewers, not here), `expiresAt` enforcement (the sign route does check and flip to `expired` on an elapsed date server-side, verify the detail page's own expiry-editing UX matches).
- Row-level chase/reminder affordance surfaced from the Signers pane directly (today it's folded into "Email all pending" only, no single-signer "send a reminder" separate from resend).

### `/contracts/templates`

**Works today:**
- CRUD for a flat list of contract-only templates: name, type, description, `{{variable}}`-bearing body via `TiptapDocEditor`.
- Search + type filter, sortable Name/Type/Updated columns.
- Used from the create-contract slide-over on `/contracts` to seed a new document with variable substitution.

**Exists but wrong or half built:**
- **`isDefault` is a real schema and API field with no UI control.** `contractTemplates.isDefault` exists on the type, `POST`/`PATCH /api/admin/contracts/templates[/id]` both accept and persist it, but neither the create slide-over nor the edit slide-over in `templates-content.tsx` exposes a toggle to set it. It is write-only from the API side today; nothing in the product tells an admin a "default" concept exists, let alone lets them use it.
- **This page is contract-only**, while the design file's template shelf (`ArtifactTemplates`) is a single shared library across Proposals, Contracts and Schedules, with its own tabbed rail, usage stats (`Used most`, `Not touched in a month`), a preview dialog per template kind, and per-kind card metadata (clause/slot counts for a contract template, slide/package counts for a proposal, week/row counts for a schedule). Porting this design correctly is a cross-group decision (it also touches the Proposals and Schedules template pages, which are in a different design-requirements group), flag rather than silently narrow-scope it to contracts alone.

**Planned or missing:**
- Templates list port per TASKS "Port only" note (catalogue: `/contracts/templates`, effort 0.5d), the unified shelf design above is the more ambitious version; a straight contracts-only port of the current page's look-and-feel against the design system is the minimum version. Both are legitimate outcomes; section 7 asks which.
- Usage counters (`uses`, last-used) do not exist anywhere in `contractTemplates`' schema or API today, a genuinely new capability if the design's "Used most" / "stale" views are wanted, not just a port. Proposal.

## 5. Data and integrations

- **`GET/POST /api/admin/contracts`**, list (org/deal/status filters, access-scoped, signer-progress aggregate) and create (from template with variable substitution, or raw `bodyHtml`; optional seeded signers).
- **`GET/PATCH/DELETE /api/admin/contracts/[id]`**, full detail with signers + signatures; partial update (body-lock enforced once sent); delete (FK cascade to signers/signatures).
- **`POST /api/admin/contracts/[id]/send`** (mint/rotate share token, flip to `sent`) and **`DELETE .../send`** (revoke: reset every signer, delete every signature, audit-log what was discarded, return to `draft`).
- **`POST /api/admin/contracts/[id]/email`**, per-signer "please sign" send through `lib/email-delivery.ts` (allowlist + suppression tracking), auto-mints a token if none exists.
- **`GET/POST /api/admin/contracts/[id]/signed-pdf`**, GET streams the R2-stored (or best-effort rebuilt) signed PDF; POST re-triggers the fully-signed email fan-out ("resend signed copy," distinct from resending a signing invite).
- **`GET/POST /api/admin/contracts/[id]/signers`** and **`.../signers/[signerId]`**, add/manage signers.
- **`GET /api/admin/contracts/[id]/preview-data`**, admin-side live-state mirror of the public viewer's data shape, bypassing the signing flow, org-scoped like every other sub-resource.
- **`GET/POST /api/admin/contracts/templates`** and **`GET/PATCH/DELETE .../templates/[id]`**, template CRUD.
- **Public (out of this group but load-bearing): `GET /api/public/contracts/[token]`, `POST /api/public/contracts/[token]/sign/[signerId]`, `GET /api/public/contracts/[token]/signed-pdf`.** The sign route is where the hash chain is actually computed and where `notifyStudioOfContractSignature` and (on the final signature) `sendFullySignedContractEmails` fire.
- **Tables:** `contractDocuments`, `contractSigners`, `contractSignatures`, `contractTemplates`. Also touches `organisations` (org name join), `deals` / `activities` (link/unlink logging, signature notification activity rows), `teamMembers` (notification recipients, creator resolution), `auditLog` (revoke forensic trail), `email_suppressions` indirectly via the delivery gate.
- **R2 (`STORAGE` binding):** signed PDF at `contracts/{contractId}/signed.pdf`, written by `lib/contract-signed-artifact.ts`, read by both the admin and public signed-pdf routes.
- **Resend** (via `lib/email-delivery.ts` / `lib/email-from.ts`): signing-invite emails, partial-signature studio notification emails, fully-signed emails to every signer and the creator with the PDF attached.
- **Per-org access scoping (`app/api/admin/_sales-access/artifact-scope.ts`):** `requireArtifactAccess`, `requireContractAccess`, `scopedOrgIds`, `filterArtifactsByScope`, `scopedOrgCondition`, this is the "Batch A" scoping STATUS and TASKS T1.16 describe as already done for contracts (along with proposals and schedules); Batch B (deals, conversations, calls, time entries, announcements) is separate work, not part of this group.
- **What must stay honest:** no fake "sent" status when `RESEND_API_KEY` is absent, `deliverEmail` reports the missing key as a real per-recipient send error rather than the route swallowing it into a false success; the UI must keep surfacing that failure rather than showing a generic "sent" toast regardless of outcome. No button should claim an action the backend does not perform, the design should not add a "Cancel contract" or "Chase" button to the shell unless the corresponding write path is built alongside it (see section 4's cancelled-status gap).

## 6. Design system contract

- **Primitives already in use, keep them:** `PageHeader`, `FilterBar` (multiselect chips + search), `DataTable` inside `Card`, `EmptyState`, `SlideOver` (48rem for create/edit forms), `ConfirmDialog`, `PromptDialog`, `Badge` (soft variant, per-type/status tone mapping), `TiptapDocEditor` for rich body editing, `TahiButton`. The detail page's `BuilderShell` / `BuilderEditorShell` / `BuilderNavGroup` / `BuilderNavItem` / `RailSection` / `FieldGroup` family is shared with the Proposals and Schedules editors and should stay shared, not fork a contracts-only variant.
- **Leaf radius and tokens:** all three pages already reference `var(--color-*)` tokens exclusively (no hardcoded hex found in any of the three files read for this pass), the design must preserve that discipline so dark mode keeps working by construction. `EmailShareModal`, `LinkedToPanel` and `HashRow` are shared components this group depends on; do not redesign them in isolation from their other callers (Proposals, Schedules, Requests all use at least one of the three).
- **What the design file gets right (`sales-artifacts.jsx`, sections "3. Contracts list" and "4. Contract editor"):**
  - A left-rail saved-views pattern (All / Out to sign / Chase list / Unfilled slots / Drafts / Fully signed / Closed / Mine) with per-view counts, matching the AR.5 rule ("filters in a left rail on every list page") that the live `/contracts` page does not yet follow.
  - A `HeadBand` KPI strip (signatures due, slots unfilled, fully signed, next to expire) giving the page a status-at-a-glance the live table alone doesn't.
