# Design requirements: client-home

Group: client-home. Audience: client. Routes: `/overview` (client half only; the same route also serves an owner "Studio Ledger" and a teammate home from `overview-home.tsx`, but those are a different audience and out of scope for this document).

Source read for this document: CLAUDE.md, STATUS.md ("Since the last update" plus the triage snapshot's "Trusted 100%" and Batch A entries), `docs/superpowers/plans/2026-09-13-page-catalogue.md` (the `/overview` row in section 2a, the Batch A block in section 4, the `/overview` lines in section 3's functionality table: teammate-home leak, daily-briefing dedup), `docs/superpowers/plans/2026-09-13-design-review-checklist.md` (Client home row), every `TASKS.md` line naming `/overview`, `client-home.tsx`, `overview-home.tsx`, or the client home cards (CA1 to CA3, T1.4, T1.3, T1.8, V1-FIX.1, T2.4/CT.7, CT.3/CT.3b, CT.16, CT.18, T2.7, T1.19, PP.2, LW.9, CA3.1), the live code (`components/tahi/overview/homes/client-home.tsx`, `components/tahi/overview/overview-home.tsx`, `components/tahi/overview/ctx.ts`, `components/tahi/overview/ov-kit.tsx`, `components/tahi/portal/home/waiting-on-you.tsx`, `components/tahi/portal/home/portal-home.css`, `lib/engagement-presentation.ts`, `lib/portal-status.ts`, `lib/client-home-signals.ts`, `lib/onboarding-steps.ts`, `lib/next-invoice-date.ts`, `lib/invoice-status.ts`, `app/(dashboard)/overview/page.tsx`, `app/(dashboard)/overview/overview.css`, `components/tahi/nav-model.tsx`), the API routes the page calls (`/api/portal/activity`, `/api/portal/requests`, `/api/portal/invoices`, `/api/portal/subscription`, `/api/portal/calls`, `/api/portal/files`, `/api/portal/team`, `/api/portal/tracks`, `/api/portal/project`, `/api/portal/onboarding`), and the Claude Design file `portal-home.jsx` (the `PortalHome` function, full read, plus `portal-home-kit.jsx`/`portal-home-data.jsx` referenced by name).

There is no `/api/portal/overview` route: unlike some other portal surfaces, this page's data model was deliberately never centralised behind one endpoint. It composes eight independent reads, each already used elsewhere in the portal, so a card fails or loads on its own schedule rather than one slow join blocking the whole page.

## 1. Purpose and audiences

Who opens it: any signed-in contact of a client organisation (`orgId !== NEXT_PUBLIC_TAHI_ORG_ID`), landing here automatically after sign-in and after onboarding completes (an incomplete onboarding redirects to `/onboarding` first, a separate surface). Also reached by a Tahi admin using "View as client" or "Act as client" (`isImpersonatingClient` in `overview-home.tsx`), which renders the identical `ClientHome` component in a read-only or write-through lens.

What it must never show:
- **Studio-internal data.** No other client's rows (every read is `orgId`-scoped server-side; see section 5). No team-wide pipeline, financial reports, or other clients' names.
- **Messages nav or a "message the team" affordance.** Messages is hidden for every client organisation by default (Liam's 2026-09-13 decision, `nav-model.tsx` line ~142, gated through the `features` map, per-org override only). The team card on this page does not offer a message button; its copy explicitly says "Questions live on the request they are about" (V1-FIX.1). A reviewer should not expect a Messages door anywhere on this page.
- **/billing and /tracks doors.** Neither is in `CLIENT_NAV`. The plan/project card never links "Manage" to `/billing`; the track queue's "need more done" CTA opens a new request, not a billing page a client cannot navigate back from (`nav-model.tsx` comments, `client-home.tsx` TrackBoard footer).
- **Money to a seat that is not an org admin.** `/api/portal/invoices` 403s a non-admin ("member") contact. The home does not fall back to "No invoices yet." for that seat: the Invoices card is dropped from the layout entirely and the Plan/Project card takes the full row (`invoicesDenied`, section 3).
- **Any figure before its own read has answered.** No card may print empty-state copy while its fetch is in flight (CT.3b); a failed read must render as an error state, never silently as zero or "all quiet" (see section 3).
- **Super-admin-only areas.** None exist on this branch of the page; the permissions builder, team access scoping, and danger-zone tooling never render here regardless of who is signed in, because this file only ever renders the client's shape of the home.
- **Write access while read-only.** Every write control (queue reorder, onboarding-step toggle, New request, Pay) is disabled both in script and visually under `ctx.isReadOnly`/`ctx.isMoneyReadOnly` (the `.ov[data-ro="1"]` wrapper plus a `disabled` prop on each control), because an admin previewing a client must not be able to act, or spend money, in that client's name except through the explicit "Act as client" write-through mode (money stays read-only even then).

## 2. Pages, sub pages and entry points

- **`/overview`** is the only route in this group. It is a client's default landing page after sign-in (there is no separate client dashboard "home" URL); an admin reaches the identical client-shaped render only via "View as client" / "Act as client" from the client detail page's impersonation controls, never by URL.
- **First-run welcome panel** (`ClientFirstRun`, inside the same page, no route or query param of its own): would render above the masthead when `ctx.home === 'first'` and the org is judged eligible by `GET /api/portal/onboarding` (`firstRunEligible`). **Currently switched off entirely** by `CLIENT_HOME_ONBOARDING_CHECKLIST_ENABLED = false` in `lib/onboarding-steps.ts` (LW.9, 2026-09-13): the component, its `/api/portal/onboarding` read, and its `localStorage` dismissal check all skip, so the page renders as if every client had already dismissed the card. Treat this as a real sub-panel that exists in code and must be designed for, not a deleted feature: it will come back.
  - Each of its four steps opens a real destination in-page: "Watch your welcome" opens the org's Loom video in a new tab (only if `onboardingLoomUrl` is set); "Share brand assets" goes to `files`; "Make your first request" opens the New request dialog on `requests?new=1`; "Confirm billing" goes to `invoices` (not `plan`/`/billing`, which is unreachable from the client nav).
- **New request dialog**: opened via `requests?new=1` from three doors on this page, namely the masthead's primary "New request" button, the "Waiting on you" tile's empty-state CTA (only when the client has zero open requests), and the TrackBoard's "Queue another" / "Slot open, submit a request" / "Ask about another track" buttons. It is not a panel owned by this page; it is the Requests page's dialog, reached by navigation with a query param.
- **Waiting-on-you tile** (`WaitingOnYou` in `components/tahi/portal/home/waiting-on-you.tsx`): not a separate route, but has its own internal expand/collapse state ("N more waiting") and its own five-state machine (loading, error, populated, empty, read-only, see section 3).
- **Row-level destinations** that leave the page: a request row opens `/requests/[id]`; a file row opens the served file URL in a new tab (`fileOpenDestination`); an unpaid invoice's "Pay" opens the invoice's hosted `payUrl` in a new tab (`invoicePayDestination`), withheld under `isMoneyReadOnly`; a call's "Join" opens `meetingUrl` in a new tab, only rendered when a link exists.
- No slide-over, sheet, or tab lives inside this page in the current code. The design file (`portal-home.jsx`) draws two sheets this page does not yet have: a "Your Scale plan" detail sheet (opened from "What is a track?" / "See the detail" / "Need more done at once?") listing plan inclusions and price, and a "Welcome to your studio" sheet that plays the onboarding Loom inline rather than opening a new tab. Neither is ported; see section 6.

## 3. States and variants

**Page-level**
- Loading: no full-page skeleton; each of the eight independent cards (masthead vitals, Waiting on you, Your work, Recent requests, Next call, Recent files, Your team, Invoices, Plan/Project) holds its own shape via `SkelRows`/`SkelFigure` until its own read answers (CT.3b, re-verified 2026-09-13). The masthead itself never loads-skeletons; it renders immediately from `ctx`/Clerk data.
- Empty, brand-new client with zero requests ever (`noRequestsAtAll`): Waiting-on-you reads "All quiet in the studio." / "Nothing here yet. Send us the first thing and you will watch every step of it from this page." with a "Make your first request" link (only when there are also zero open requests). TrackBoard/ProjectBoard show their own first-run-flavoured empty copy.
- Empty, steady-state client with nothing pending: Waiting-on-you reads "All quiet in the studio." / "Nothing is waiting on you right now. We will tell you the moment there is something to look at." with no CTA if the client has open requests elsewhere on the page.
- Error, per-card: each of the eight reads fails independently and renders its own `CardError`/inline error with a "Try again" that revalidates only that read (never blocks the rest of the page). The Waiting-on-you tile has its own error state that outranks its empty state ("Your overview did not load. That is on us, not you... Try again.").
- Error, review signal specifically: only shown when BOTH the active-requests read and the dedicated client_review read have failed (`reviewSignalFailed`); one succeeding is enough to trust the count.
- Read-only (admin "View as client"): every write disabled via `.ov[data-ro="1"]` plus per-control `disabled`; Waiting-on-you and the onboarding checklist show a "You are reading this as {org}. Every action here is read-only in client view." note.
- Read-only, money only ("Act as client" write-through): `ctx.isMoneyReadOnly` disables only the Pay buttons (masthead/tile/invoices card) and reorder/new-request/checklist controls stay live; this is a distinct combination from full read-only and must render correctly (Pay greyed with a title tooltip, everything else interactive).
- Member seat (not org admin): the Invoices card in the Billing zone does not render at all once the read resolves to a 403 (`invoicesDenied`); the Plan/Project card takes the full 12-column row in its place. No "denied" message card is shown on this page (contrast with `/invoices`, which does show one); the client simply never learns money exists on this page.
- Admin seat: Invoices card renders at 7 columns beside a 5-column Plan/Project card.
- Retainer client (`clientType==='retainer'` from `/api/portal/subscription`, or an unprovisioned custom-priced client per `lib/engagement-presentation.ts`): "Your work" zone renders TrackBoard; Billing zone's second card reads "Your plan".
- Project client: "Your work" zone renders ProjectBoard (phases); Billing zone's second card reads "Your project" with phase/milestone/next-invoice subrows; the masthead vitals gain a "Project progress" tile.
- Xero-rail retainer with no `currentPeriodEnd`: "Next invoice" projects a real date from cadence (`lib/next-invoice-date.ts`) rather than showing "TBC"; only with neither a period end nor a period start does it fall back to naming the rail ("Invoiced monthly through Xero") (CA3.1).
- 375px: container-query breakpoints at 46rem collapse every card to full width, the vitals strip wraps to a 2-up grid, the zone side-rail label hides, masthead reflows to stacked, Pay buttons and queue reorder buttons grow to the 2.75rem (44px) touch minimum (`overview.css` lines ~427-460).
- 768px: the 66rem container-query breakpoint drops cards from 7/5/8/4-column spans to 6/6; the 46rem breakpoint (roughly tablet-portrait and below) is where the full single-column collapse happens, so a 768px-wide reviewer viewport sits in the two-column regime, not the stacked one.
- Dark mode: `.ov` carries a `.dark .ov` override for `--bg-tertiary` only; every other token is a shared CSS variable, so the page should need no other override. The Waiting-on-you tile is a deliberately fixed-dark forest surface in BOTH themes (documented in `portal-home.css` beside the sidebar exemption); a reviewer should not flag it for "not respecting light mode," that is intentional.
- Print or public: not applicable. This page has no print stylesheet and is never reachable outside an authenticated client or admin-preview session.

## 5. Data and integrations

- **`GET /api/portal/activity`**: the "Lately" wire strip at the top of the masthead area (`TheWire`), org-scoped.
- **`GET /api/portal/requests?status=active&limit=200`** and **`GET /api/portal/requests?status=client_review&limit=200`**: two independent reads against the `requests` table (org-scoped), the second specifically so a stale, page-one-dropped `client_review` row can never silently vanish from the review count.
- **`GET /api/portal/invoices?status=all`**: `invoices`/`invoiceItems`, gated by `requirePortalFeature(..., 'invoices')` and `isOrgAdmin`; 403 for a non-admin seat, read as "denied," never "empty."
- **`GET /api/portal/subscription`**: `subscriptions`, `organisations.customMrr`/`planType`, resolves `clientType` (retainer/project), plan label, billing interval, invoice channel (`stripe`/`xero`), monthly rate and currency, track count.
- **`GET /api/portal/calls`**: `scheduledCalls` (Batch 4 schema), org-scoped, filtered to the next upcoming call with attendee names.
- **`GET /api/portal/files`**: `files` table (R2-backed), org-scoped, most recent uploads.
- **`GET /api/portal/team`**: the studio team members assigned to this client's account (via client PM/assignment, not team-wide).
- **`GET /api/portal/tracks`** (retainer only): `tracks` rows plus their current/queued `requests`, `PUT /api/portal/tracks/[id]/reorder` for queue reordering.
- **`GET /api/portal/project`** (project clients / unprovisioned custom-priced clients only): `projects`, published `projectSchedules` snapshot only (`status='shared'`, CT.7/T2.4), never a live draft.
- **`GET`/`PATCH /api/portal/onboarding`**: `organisations.onboardingState`/`onboardingLoomUrl`, currently unreached because the checklist is flagged off.
- **Currency**: every native amount renders through `DisplayCurrencyProvider`/`useDisplayCurrency` (`Money` component, `formatNative`), never a hardcoded FX rate; a negotiated custom-currency retainer shows its own currency plus a display-currency equivalent, never a silently converted figure.
- **Third parties, indirectly**: Stripe (invoice `payUrl`, when the org is on the Stripe rail) and Xero (the billing cadence used to project "Next invoice" when there is no Stripe period). Nothing on this page calls Stripe/Xero directly; it reads what the portal API routes have already resolved.
- **Must be honest**: no fake numbers (every vital is either a real count or withheld), no dead buttons (every CTA on this page opens a real dialog, a real route, or a real external URL; the historical dead "Message the team" CTA and the historical "Manage"-to-`/billing` link are both gone, per V1-FIX.1 and the `nav-model.tsx` comments).

## 6. Design system contract

- **Primitives already in use**: `PageHeader`-equivalent masthead pattern (bespoke `.pfh-mast`, not the shared `PageHeader` component, since this is a home page rather than a list/detail page), `Zone`/`Card`/`CardH`/`Row`/`Vitals`/`TheWire` from `components/tahi/overview/ov-kit.tsx` (shared with the owner and teammate homes), the leaf-radius family is present on the Waiting-on-you tile's clipped leaf watermark and the empty-state leaf icon, tokens are used throughout (`var(--text)`, `var(--brand)`, etc., with only a few inline hex values for one-off type treatments inside the Plan card that should be tokenised if touched).
- **What the design file gets right** (critic verdict: SHIP, Pass 3, "strongest page in the walk"): the dense, single-scroll composition (masthead, first-run, wire, hero, vitals, work, activity, library, billing, all on one page with no tabs); the hero-tile idiom for "Waiting on you" as the one thing a client must act on, replacing a KPI-plus-repeated-list pattern; the ranked, capped-at-three-with-expander list inside the hero; the ratio of Card spans across the grid (12 / 7+5 / 6+6 / 7+5).
- **What the design has that the port lacks, and should be decided before the next design pass**: the "Your Scale plan"/"Your project" detail sheet (a slide-over with the full plan inclusions list and price, opened from three separate doors); the inline "Welcome to your studio" video sheet (plays the Loom in-panel instead of a new tab); the dismissible studio-notice/announcement banner. None of these are in the live code today; a reviewer should not mark the live page FIX for lacking them unless Liam has actually asked for them (mark any recommendation to add them "proposal").
- **What must change from the design as ported**: the design hardcodes exactly two track lanes ("Track one"/"Track two"); the real page supports N tracks and must keep doing so, so any new design pass must draw a 3+-lane state, not just the two shown. The design's Pay/Join/Approve buttons in the hero use the shared `Btn` kit component; the ported code's equivalent buttons (`pfh-btn`) are hand-rolled to this tile only, worth folding into the shared kit if a design refresh touches this file, but not a defect today.
- **Touch targets**: the one payment-reaching control on this page (`.ov-cta.ov-pay`) is deliberately compact (1.75rem) on a fine pointer inside a dense invoice row and grows to 2.75rem (44px) under `@media (pointer: coarse)` and again under the 46rem container query, so a reviewer measuring it at 1440px with a mouse cursor is intentionally seeing the small size; measure it in a touch/narrow context instead.
