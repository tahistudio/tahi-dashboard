## How the run executes (budget rules)

- Mode: normal, not ultracode. One builder per item on sonnet where the brief is fully specified (A3, A5 lap script, B3, B5, C3, C4), opus where money, auth or tenancy is touched (A1, A2, A4, B1, C1, C2). One reviewer only for A4, C1 and C2. No adversarial multi-vote passes, no design critics.
- Batching: items merge into main in batches of three or four and go through ONE gate and ONE deploy per batch (a gate plus deploy costs the same whether it carries one item or four). Strict chain every time: set -o pipefail, build under a 900 second timeout, type-check, worker tsc, lint zero errors, vitest with a single --last-failed retry, commit from a message file, push, watch, health probe (sign-in 200, unauthenticated overview 307), smoke.
- Migrations: additive and idempotent, mirrored in the registry, applied to both D1s before the push, statement by statement (staging retries on the wrangler auth flake).
- Data writes on production only through the app's endpoints as Liam in a dedicated browser tab, dry run first, never through wrangler.
- Budget checkpoints: after each batch, log spend against the weekly limit in the run log. Stop taking new items at 60 percent of the weekly limit and finish only what is in flight, so the working week keeps at least a third.
- Expected cost at this mode: Batch A about 12 to 15 percent of the weekly limit, Batch B about 15, Batch C about 8, Batch D whatever is left. The overnight designs cost more than this whole plan because every surface had five agents; this run averages under two.

## Risks and what happens to them

- A builder hangs: 30 minutes without journal writes means stop and resume from cache; a hung next build is killed by the timeout.
- A batch fails its gate: the batch is bisected by item, the failing item is dropped to the next batch, the rest ships.
- Liam's decisions missing: defaults above apply and the item is marked with the assumption in the run log.
- The weekly limit: checkpoints above; nothing destructive is ever left half applied because every data change is dry run then apply inside one endpoint call.
